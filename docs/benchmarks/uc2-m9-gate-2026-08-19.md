## What the gate measures

Spec: `docs/superpowers/specs/2026-08-19-uc2-production-readiness-design.md` §4.
Plan: `docs/superpowers/plans/2026-08-19-uc2-m9-deployable-node.md`.

M9 makes the node **deployable**: a real `uc2-node` binary that starts from a
config file, refuses a misconfiguration at startup instead of failing later in
a way that looks like something else, and stops cleanly on `SIGTERM` so a
restart rejoins from the journal rather than paying reconstruction.

M9 changes no consensus, wire-protocol, or cnc-page surface. It is additive:
new modules and binaries plus one new method on `Node`. That is why this gate
measures **operational cost and refusal behaviour**, not safety — safety is
already held by the sim, the lincheck capstones, the crashtest, and the Lean
proofs, and none of those are weakened by a milestone that adds a `main`.

## The bar

Pre-committed. Four rows, all must pass.

| # | Measure | Bar |
|---|---|---|
| 1 | `SIGTERM` → process exit, leader under sustained load | **< 1 s**, exit code **0** |
| 2 | Snapshot install on restart | cnc `incoming_snapshot_pos` (offset 1280) **unchanged** across the stop+restart cycle |
| 3 | Cluster commit-rate dip across the stop+restart window | **< 10 %** |
| 4 | Config refusals | every preflight rule refuses with a message **naming the offending field** |

### Why each row is the right bar

**Row 1 — under load, not idle.** A drain measured on a quiescent node proves
nothing: the archive has nothing to catch up on. The stop must be issued while
the node is the serving leader taking writes, which is when the archive is
furthest behind. 1 s is the operational bar — a supervisor's stop must not feel
like a hang — and it must be met with the drain's default 5 s budget available,
so a PASS means the drain *finished*, not that it timed out.

**Row 2 — the row that makes the drain worth having.** A node that stops
cleanly holds every acked byte in its journal, so on restart it replays a short
tail. A node that did not drain may fall behind the leader's purge floor and
have to be served a **snapshot** instead. `incoming_snapshot_pos` is the
evidence: it moves only when a snapshot session is installed. Unchanged across
the cycle means the restart cost was replay, not reconstruction. This is the
one row that would catch a `stop_draining` that silently degraded to `stop()`.

**Row 3 — the M6/M7 dip bar, unchanged.** A planned leader stop costs one
election timeout (150–300 ms) because M9 deliberately ships **no leadership
transfer** — that is a consensus change and is out of scope. Reusing the
established 10 % bar keeps this comparable to the M6 learner-join dip (0.9 %)
and the M7 transition dips (0.0–4.7 %). A dip materially worse than those means
the clean stop cost more than the election it was supposed to cost.

**Row 4 — refusals are a feature, so they are gated.** M9's premise is that a
named startup refusal beats a confusing downstream failure. That premise is
only true if the refusal actually names the field. Each rule is driven with a
config that violates exactly it, and the message is checked for the field name.

## Honest-failure protocol

Adopted verbatim from M7, which this project learned the hard way when its
first fleet run was a 100 % harness artifact:

- The gate binary prints the bar and `exit(1)` on FAIL. A green terminal is not
  a PASS; the exit code is.
- A FAIL is diagnosed before it is re-run. Harness defects and genuine
  properties are separated and both recorded.
- A local run is **smoke**, never the gate. It proves the harness wires up; it
  does not produce the number, because a single box cannot show cross-host
  restart cost.

### Diagnosis: the harness's load model, with a residual product question

The run's own log carries the tell: **leadership moved to n1** during the
restart. The harness ran ONE load client pinned to the leader and, on failover,
tore it down and respawned it on the new leader — paying a process spawn plus
its CAN_SERVE wait **inside the 5 s measurement window**. That cost was charged
to the cluster.

That load model was wrong about what `uc2_client` is. It is an SDK for a
**per-node app client**: every node runs one, the leader's serves requests, and
a follower's answers its callers with a redirect to the leader. Fixed in commit
`10d3d9d`, two parts: the orchestrator now starts a client on **every** node
and touches none of them across the restart (the new leader's client simply
starts serving); and `m9_gate`'s `load_loop` gained a 2 ms backoff in its
`NotLeader` arm, because the fleet role registers only its own node and a
follower's client would otherwise hot-spin connect/submit/NotLeader/shutdown
with no sleep — burning a core on every non-leader host and perturbing the very
commit rate row 3 measures.

**The fix is reasoned from the fleet log, not demonstrated.** The dev box
cannot measure row 3 (Ruling 12: seven identical local runs spread 0.0–18.0 %
against a 10-point bar; with the per-node client model it reads ~90 % under
nine busy-spin processes). Only fleet run 2 can confirm it.

### Open question before fleet run 2

The 10 % bar was inherited from M6/M7 — transitions in which **no node goes
away** (a learner joins; membership changes one at a time). A leader *restart*
removes the serving node: it forces an election (150–300 ms timeout, since M9
deliberately ships no leadership transfer) and, under the per-node client
model, requests arriving at followers during the gap are redirected to a leader
that is not serving yet. Some dip is therefore a **real product property**, not
harness noise.

To answer in writing before hardware is booked again: is `< 10 %` over a 5 s
window the right adjudication for a restart, or should row 3 be re-specified —
e.g. dip over a longer window, or time-to-recover-baseline? Per the
honest-failure protocol, any change to the bar must be **pre-committed in this
document before fleet run 2, in its own commit**, and must not be derived from
run 1's 62 % ex post. Run 1 stays a FAIL against the bar it ran under either
way.

**Answered 2026-08-19 (maintainer decision, this commit, before fleet run 2):
row 3 is re-specified as time-to-recover.**

## Row 3 as re-specified for fleet run 2 (pre-committed)

| # | Measure | Bar |
|---|---|---|
| 3 | Time from `SIGTERM` until the cluster commit rate is back at baseline | first qualifying window **ends ≤ 15 s** after the `SIGTERM`; the next window must also qualify |

Definitions, fixed before the run:

- **Baseline**: one 8 s on-host rate window on a **survivor** (a node that is
  not being restarted), taken immediately before the stop. Survivors track the
  cluster's commit frontier whichever node leads, so this is cluster rate, not
  one node's.
- **Qualifying window**: a 2 s on-host rate window on the same survivor whose
  rate is **≥ 80 % of baseline**.
- **Recovered**: the first qualifying window whose *end* falls within **15 s**
  of the `SIGTERM`, **and** the immediately following 2 s window also
  qualifies (one lucky window is not recovery). Only the first window's end is
  bounded by the 15 s budget.
- The run-1-style 5 s dip is still measured and **printed, ungated**, for
  comparability with run 1.

Why these numbers — derived from the operation and the plumbing, **not** from
run 1's 62 %:

- **15 s budget**: M6/M7 give whole membership operations a 10 s bar. A
  restart's product cost is stop (< 1 s, row 1) + election (150–300 ms) +
  client redirect convergence. The orchestrator adds unavoidable measurement
  plumbing before the first window can even complete — the restart action is
  ~3 ssh round trips (~3 s) and each poll is one ssh exec around a 2 s on-host
  window (~3 s wall) — so the earliest *observable* recovery sits at ~6 s even
  for a cluster that recovered instantly. 10 s of operation budget + ~5 s of
  measured plumbing, rounded to 15. All skew inflates the measurement, i.e.
  errs **against** PASS.
- **80 % threshold / 2 s windows**: 1 s windows are too noisy to threshold at
  90 % (client batching alone moves short-window rates by more than 10 %);
  2 s windows at 80 % with a second confirming window is robust to window
  noise while still meaning "the cluster is back to doing its job".
- **Why time-to-recover at all**: what a planned restart costs an operator is
  *how long the cluster runs degraded*, not the depth of a fixed 5 s average
  that mixes the outage with the measurement window's tail.

Cost if wrong, stated up front: 15 s is generous — a cluster taking 14 s to
recover passes. Accepted: this row's job is to catch pathological restart cost
(the run-1 alternative hypothesis was minutes-long rejoin via snapshot), not to
micro-benchmark the election; rows 1 and 2 already bound the stop and the
rejoin path. FAIL prints the full window timeline so a red run is diagnosable.
