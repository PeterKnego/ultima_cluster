## What the gate measures

Spec: `docs/superpowers/specs/2026-07-09-uc-v2-aeron-shaped-smr-design.md`
(architecture) plus M10's scope note in
`docs/superpowers/specs/2026-08-19-uc2-production-readiness-design.md` §5.
Plan: `docs/superpowers/plans/2026-08-19-uc2-m10-observable-cluster.md`.

M10 makes the cluster **observable**: a Prometheus-text `/metrics` endpoint
over the held cnc page and process counters, role-aware `/healthz`/`/readyz`
probes that refuse the `0x01` (elected, not yet `CAN_SERVE`) window a naive
probe would call ready, structured JSON-lines logging at consensus
transition sites, and a shipped set of Prometheus alert rules + a Grafana
dashboard. M10 changes no consensus, wire-protocol, or cnc-page surface — the
exporter only reads through `Arc`s and atomics the hot-path agents already
own, and the HTTP server shares no lock with them. That is why this gate
measures **observation completeness and observation safety** (does the
contract actually get exported; does the probe ever lie during a leader
transition; do the rules actually fire), not consensus safety — that is
already held by the sim, the lincheck capstones, the crashtest, and the Lean
proofs, none of which are touched by a milestone that only reads.

## The bar

Pre-committed (plan commit `b96595b`, before implementation). Four rows.

| # | Measure | Bar | Adjudicated |
|---|---|---|---|
| 1 | `/metrics` coverage | every family in `CONTRACT_SERIES` present in a live scrape of a serving 3-node cluster, plus ≥1 occupied per-peer series on the leader | local |
| 2 | Probe regime across a leader kill | under load, kill the leader; a 100 Hz poller on every node's `/readyz` observes **zero** samples where a 200 coincides with that node's flags reading `0x01` (poller reads flags via a second read-only cnc attach in the same sample); some node serves 200 within 5 s | local + repeated on the fleet |
| 3 | Scrape perturbation | M5-gate A/B on the same fleet, scrape-on (1 s interval, all nodes) vs scrape-off, back-to-back: throughput ratio ≥ 0.95 (the same-fleet A/B method that resolved the M5 client-extraction question; cross-fleet comparisons are noise) | **fleet only** |
| 4 | Alert rules | `scripts/m10_alert_fire.sh` exits 0 — every shipped rule fired once, scenario table as pre-committed (synthetic states disclosed by name) | local |

### Why each row is the right bar

**Row 1 — the contract is the product.** `CONTRACT_SERIES` is M10's
machine-readable promise: every name an operator's dashboard or alert rule
can reference. A family missing from a live scrape is a broken promise no
amount of code review catches, because the encoder and the contract list can
drift independently. The per-peer assertion exists because the labeled
families (`uc2_peer_reported_durable_bytes` etc.) are conditionally emitted —
present only for occupied slots — so a coverage check that never puts load
on the cluster could pass vacuously with zero peers ever exercised.

**Row 2 — the spec's named naive-probe failure.** The whole reason
`/readyz` exists as a *role-aware* probe rather than "is this the leader" is
the `0x01` window: a node that has just won an election but whose `NewTerm`
frame has not yet quorum-committed is elected but cannot correctly answer a
linearizable read. A supervisor or load balancer that routes on leadership
alone would serve from that node during the gap. This row is a direct test
of the failure the endpoint was built to prevent — read the flags with an
*independent* cnc attach in the same sample as the HTTP call, because the
whole point is to catch the endpoint racing its own state, not to trust the
endpoint's self-report.

**Row 3 — cache traffic is a cross-host claim.** "Reads cannot perturb the
hot path" is a statement about NIC interrupt load, cache-line traffic from a
scraping thread, and OS scheduling contention under a real network stack —
none of which a single dev-box process can honestly produce. The M5-gate
same-fleet A/B method (which resolved the M5 client-extraction parity
question) is the only method this project trusts for exactly this class of
claim, so row 3 is fleet-only by construction, not by caution.

**Row 4 — an alert that has never fired is documentation.** A rule with a
typo'd label, a wrong comparison operator, or a `for:` window the real
metric shape can never sustain looks identical to a correct rule until
someone is paged by neither. Driving every shipped rule through the real
exporter and letting `promtool` adjudicate is the only way "the alert
exists" becomes "the alert works."

## Honest-failure protocol

Adopted verbatim from M7/M9:

- The gate binary prints the bar and `exit(1)` on FAIL. A green terminal is
  not a PASS; the exit code is.
- Bar and result are recorded in separate commits, bar first (this document,
  before the harness).
- A FAIL is diagnosed before it is re-run. Harness defects and genuine
  properties are separated and both recorded.
- A local run of row 3 is **smoke**, never the gate. The dev box measured an
  18-point run-to-run spread against a 10-point bar for M9's comparable
  fleet-only dip row (M9 gate doc, Local smoke section) — the same box, the
  same reason: a measurement noisier than the bar cannot adjudicate it in
  either direction. Row 3's local numbers here are printed **ungated** and
  labeled **SMOKE**.
- `v2.4.0` tags only when the fleet rows (row 2 repeated, row 3) pass, and
  tagging is the maintainer's step — not performed by this document or by
  landing this branch.

## Task 9 scenario disclosure table

Every alert rule fires through the real Prometheus-text exporter and a real
HTTP scrape; the *broken state* behind the scrape is genuine cluster
brokenness where that's honestly constructible in-process inside this
harness's budget, and synthesized (injected `ObsSources` fields, disclosed
by name) where it is not. This mirrors the elle gate's precedent of
recording structural-can't-expose findings rather than pretending coverage.

| Rule | State | Scenario |
|---|---|---|
| Uc2NoLeader | **real** | 3-node cluster; `Node::crash()` the leader and one follower — the lone survivor is a minority and never re-elects |
| Uc2ServiceWedged | **real** | real node + a real attached service; `Service::stop()` halts the apply agent while the node keeps polling |
| Uc2ReplicationStalled + Uc2AdmissionSaturated | **real** | 3-node cluster under load; partition the leader from BOTH followers (deliberately tiny admission window) — the leader keeps appending while commit stalls |
| Uc2PeerLagging | **real** | 3-node cluster under load; fully isolate ONE follower (both links) while the leader and the other follower keep committing |
| Uc2PeerNeverHeard | **real** | 3-member static config where one member's address is bound-then-dropped — known, never started; the running nodes' cnc peer slot for it is latched occupied but never reports |
| Uc2AgentDead | **synthetic, disclosed** | synthetic `ObsSources`: the archive agent's liveness flag flipped directly (a real fail-stop is a much bigger harness than an alert test warrants) |
| Uc2LeaderNotServing | **synthetic, disclosed** | synthetic cnc page: flags `0x01` (elected, no `CAN_SERVE`) served through the real exporter — the real state is a sub-RTT race window the seeded fault layer cannot cut selectively |
| Uc2PurgeStalled | **synthetic, disclosed** | purge-enabled synthetic sources with floor − first_base > 2 segments (driving a real stall requires breaking the archive mid-run) |
| Uc2RepeatedWipes | **synthetic, disclosed** | the wipes counter bumped directly (no compact real `NoCommonPrefix` wipe-and-rejoin scenario fit the harness's budget); the 0→3 TRANSITION is two genuine live HTTP scrapes before/after the bump |
| Uc2UnattestedReports / Uc2CleartextPeer / Uc2FollowerSealFailures | **synthetic, disclosed** | counters bumped directly through the real encoder — the real triggers (a 0.4.0 peer, a mixed-crypto cluster, a corrupting adversary) are not honestly hostable in-process |

**Time-dilation method.** `m10_alerts.rs` captures raw, unmodified real
scrape values over a short bounded window (~1 Hz, ~10–15 s). Turning those
into `promtool`-sized `input_series` timelines (holding the last real value
constant for as long as a rule's `for:` window needs, or placing a real
observed jump inside a delta-range window and continuing a small synthetic
ramp so the condition stays true for the rest of the sustain) is
`scripts/m10_alert_fire.sh`'s job and never touches what got scraped. Every
dilation decision is printed at runtime as a `dilate` line naming the rule,
series, policy, window, and which real value it is holding or ramping from —
so a reviewer can see exactly where the real measurement ends and the
synthetic timeline extension begins.

## Two observations recorded from the work

- **Harness discovery, not an M10 defect.** UC's leader election has no
  pre-vote or leader-stickiness check — a candidate is granted a vote purely
  on term+log currency. The first version of the `follower_partitioned`
  (Uc2PeerLagging) scenario cut only the leader↔victim link; the victim's own
  heartbeat timer lapsed almost immediately once it stopped hearing the
  leader, and it legitimately canvassed the third node and stole the term —
  even though that third node was still hearing the real leader the whole
  time. Reproduced every run. The harness now fully isolates the victim
  (both links) instead, which is what a real network partition of one
  follower looks like anyway. This is a product observation about UC's
  election design (no pre-vote), not a bug M10 introduced or needs to fix.
- **`ObsSources` gained `Clone` as public API.** Additive: the HTTP server
  thread owns one `ObsSources` by value (no lock shared with the hot-path
  agents), while callers that need a second handle — tests, and this gate's
  own scenario code — clone it; every clone shares the same underlying `Arc`
  allocations, so it never diverges from the source.

scrape (zero missing); the `uc2_peer_reported_durable_bytes{peer=...}`
substring check for an occupied per-peer sample also held (the harness
asserts presence, not an exact per-peer count — a 3-node cluster gives the
leader up to 2 possible peer slots, and at least one was occupied every
run). Reproduced on every gate run, including the reviewer's independent

### Row 2 — probe regime across a leader kill

`cargo run -p uc2_node --release --example m10_gate -- probes`: 3-node
cluster + obs servers under a modest submit load; `Node::crash()` the
leader; for up to 5 s, poll every surviving node's `GET /readyz` and, in the
same sample, read that node's flags via a second read-only
`CncPage::open_file` attach. The poller *attempts* ~100 Hz but each sample
pays a fresh TCP connect against the obs server's HTTP accept loop, which
polls its listener at a 100 ms cadence (`uc2_node/src/obs/http.rs`,
`ACCEPT_POLL` — chosen there so `ObsServer::stop()` returns promptly, not
for probe throughput); effective aggregate sampling is closer to **~10 Hz**
across the two survivors, not 100 Hz — see "Non-vacuity check and its
margin" below.

**PASS** — 100 samples across 2 survivors over the 5 s window, **zero**
samples where `readyz==200` coincided with `flags==0x01`
(`NODE_FLAG_LEADER` without `NODE_FLAG_CAN_SERVE`) on any surviving node;
some node served 200 at **~0.09–0.10 s** into the window (0.093–0.099 s
across runs), comfortably inside the 5 s budget.

**Non-vacuity check and its margin (added on top of the pre-committed
bar).** The harness counts `windowed_samples`: samples where the
independent cnc-attach read showed `flags==0x01`, *regardless of the
readyz status observed*, and requires `windowed_samples > 0` to PASS. This
is a strengthening of the row, not a change to the bar text above: the
pre-committed bar says "zero samples where a 200 coincides with `0x01`",
which a run that never sampled inside the `0x01` window at all would
satisfy vacuously (0 violations because 0 opportunities to violate) — the
same failure mode the coverage row's per-peer assertion exists to rule out
for row 1. The non-vacuity check makes that vacuous case a FAIL instead of
a silent PASS.

Measured margin: **exactly 1 in-window sample per run**, out of 100 total
samples, reproduced across 4 independent runs (3 here, 1 by the reviewer).
Root cause of the tightness is the cadence arithmetic above: the `0x01`
window itself is short — from the real run logs, `became_leader` to
`serving_changed` is on the order of ~100 ms (e.g. one run:
`became_leader` at term=2 base=19232, `serving_changed` ~102 ms later) —
which is comparable in size to the obs server's own 100 ms accept-poll
granularity, so only about one poll round out of ~50 lands inside the
window.

**Disclosed consequence.** A slower or more heavily loaded box may cause
this row to flake red by landing zero samples in the window on an unlucky
run. If row 2 goes red, **check `windowed_samples` in the printed detail
line before suspecting a product regression** — `windowed_samples == 0`
with `violations == 0` means the check didn't get to run, not that the
product failed it. Widening the margin (persistent per-target connections
instead of a fresh TCP connect per sample, or repeating the leader-kill N
times in one gate run to get N independent shots at the window) are both
named here as options for a future maintainer/fleet-orchestrator decision,
not applied in this round — this document records the diagnosis, it does
not change the harness or the product's `ACCEPT_POLL` cadence.

## Fleet runs — 2026-08-20

Fleet: 3×`c6id.2xlarge`, us-east-1 (`make up-uc`, `node_count = 3`), driven by
`bench-infra/scripts/m10_fleet_gate.py --fleet --row all`. The orchestrator
adds a third fleet row beyond this document's original two — **row Q,
quiet-on-healthy** (final-review recommendation): a healthy loaded cluster
runs ≥10 minutes under a real Prometheus 3.5.0 on node0 scraping all three
nodes' private-IP `:9600` at 1 s with the shipped `uc2-alerts.yml` loaded
verbatim, and the row passes only if **zero alerts fire** and **every
`CONTRACT_SERIES` family is ingested from all three instances**. This is the
row whose absence let the follower false-fire defect (above) survive to the
final review, and it doubles as the spec's "scraped by Prometheus in a fleet
run" acceptance evidence. Fleet destroyed the same day;
`terraform -chdir=terraform state list` printing nothing is the completion
check.

**Run 1 — harness crash (recorded).** Rows Q and 2 executed; row 3's first
fresh-cluster start died on `m6_fleet_gate.wait_leader`'s strict split-brain
check: a freshly deposed `uc2-node` keeps its leader/can_serve flags until it
hears the new term (no check-quorum step-down; the read barrier, not the
flag, protects reads), so a contested election shows a transient two-serving
view the checker treated as fatal. A second harness defect compounded it:
verdicts printed only in the end-of-run table, so the crash also discarded
the completed rows' verdict lines. Both fixed (`wait_single_leader`, per-row
verdict printing) before run 2. Run 2's diagnosis later showed run 1's row Q
had also been silently degraded (below).

**Run 2 — FAIL (honest, recorded): rows Q and 3 down to harness config; row
2 PASS.** The orchestrator had shipped the local smoke's toy sizing (4 MiB
ring, **16 KiB journal segments**) to the fleet under the full m5 client
pump. Segments rolled at kHz (1011 files on disk), and because the journal
holds an fd per segment, the daemons hit `EMFILE` against systemd's default
1024 soft limit and fail-stopped 15–90 s into load — **M10's fail-fast
worked exactly as designed** (`agent_failstopped` records, exit 1). Node0's
daemon died 8 s into the soak, so Prometheus read `up == 0` for the whole
window: row Q reported an honest 0/62 coverage and its `firing alerts = 0`
was vacuous. Row 3's arm A found no leader amid the resulting election churn
(terms 12–15). The product endpoint was verified healthy in isolation: a
manually started daemon on the same host served `/metrics` and `/healthz`
and elected at term 1. **Row 2 passed** (3 kills, 0 violations, non-vacuous
in-window sampling each kill, first-200 within 46–136 ms). Fixes,
pre-committed before run 3: production sizing in the rendered TOML (64 MiB
buffer, 64 MiB segments, both modes so the smoke matches the fleet) and
`LimitNOFILE=65536` on the daemon units, mirroring
`packaging/systemd/uc2-node.service`. Operational finding worth keeping:
**fd-per-journal-segment is a real daemon characteristic** — the packaged
unit's nofile limit with 64 MiB segments gives ~4 TB of un-purged journal
headroom, and purge is the real answer.

  non-vacuous, but a future red run should check `windowed_samples` first.
