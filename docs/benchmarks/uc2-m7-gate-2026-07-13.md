## What the gate measures

Spec §9.6 (`docs/superpowers/specs/2026-07-13-uc2-reconfig-design.md`):

| # | deliverable | gate |
|---|---|---|
| M7 | live single-server reconfiguration | replace-a-box + resize 3↔5 + leader self-removal, all under sustained load |

M7 is the milestone that makes cluster membership a **live, online operation**
instead of boot-time-only configuration. It closes v2.0's one accepted
capability regression against the reference design's original ambition
("static voting set … joint-consensus reconfiguration is v2.x" — the v2.0
README/CLAUDE.md scope line this milestone rewrites). Unlike v1 (which never
shipped dynamic membership) and unlike **OSS Aeron Cluster**, which shipped
"dynamic join" (passive members + log-recorded membership events —
structurally the same idea) and then **deprecated it in 1.41 and removed it in
1.42 (2023)** as never production-quality — current Aeron is static-membership
with offline procedures, and its vendor's production answer for replacement
moves the operation *out* of the consensus protocol entirely. M7 deliberately
exceeds the reference here: the bet is that the membership × snapshot ×
truncation × recovery integration surface that sank Aeron's version is exactly
what `uc2_sim` + the WGL capstones + the crashtest were built to hold.

The three fleet scenarios, and how each is proven locally first:

1. **replace-a-box** — add a learner on a 5th host, catch it up, promote it to
   voter, remove a (crashed) original voter. Fleet gate: commit-rate dip
   **< 10 %** across every transition window, zero read divergence.
2. **resize-3-5-3** — two add+promote pairs (3→5 voters), then two
   demote+remove-learner pairs (5→3), landing back on the original ids. Same
   bars as replace-a-box.
3. **leader-self-removal** — the serving leader removes itself. Fleet gate:
   zero committed loss; new leader serving **< 10 s** (the measured gap is
   reported regardless — it is the existing ~200 ms failover class, not a new
   number to hit).

## Correctness proofs (local, green)

### Sim: inv6–9 + counterfactual-red pins (the mechanism proof)

`uc2_sim` models config frames as data (adoption-on-durable, rebuild-at-boundary,
revert-on-truncate) with four new invariants alongside inv1–5:

- **inv6** config determinism — adopted config equals the durable-frontier-implied config.
- **inv7** quorum legality — commit only advances via a quorum of the adopting config, config-aware (generalizes the old phantom-commit oracle).
- **inv8** revert correctness — after any truncation, adopted config re-equals the frontier's config.
- **inv9** tombstone permanence — a tombstoned id never re-enters.

Counterfactual-red pins (the C-1 discipline — delete a guard, assert the
invariant goes red):

- `counterfactual_no_serving_gate_produces_disjoint_quorum_commit` — Ongaro's
  2015 correction staged mechanically (an isolated leader proposes a promote,
  crashes before the frame commits; with the serving gate disabled, a second
  leader commits a REMOVE on a disjoint 2-of-3 quorum) — asserts the inv7
  violation. `serving_gate_refuses_the_premature_proposal` is the guarded twin
  (same instant, gate ON → `Err(NotServing)`, stays green).
- `counterfactual_no_revert_breaks_inv8` — deleting revert-on-truncate on the
  identical divergent-leader trace asserts the inv8 violation.

Plus `add_promote_demote_remove_cycle_under_faults` (crash + partition between
steps, both removed nodes `halted_removed`, survivors converge and keep
committing, re-adding a tombstoned id refused) and
`propose_during_pending_is_refused`. **Fuzz arm:**
`fuzz_heavy_config_churn` (sim-heavy) — 1000 seeds, random legal + illegal
config ops (one guaranteed-illegal op per round asserted `Err`) from random
nodes under drop/dup/crash churn; refused-never-adopted pinned
(`node_config_version(i) <= accepted` for every node); all invariants green.
The fuzz arm **genuinely bit** during development: seed 0 went red on first
run, exposing a real oracle-vs-mechanism mismatch in the initial inv7 (the
mid-self-removal leader's "+1 own slot" tracker rule was stricter-checked than
the mechanism warrants) — fixed in the oracle, not the mechanism. That is the
milestone thesis working mechanically, not anecdotally.

```
cargo test -p uc2_sim                                → 20 + 18 + 0 doc, all green
cargo test -p uc2_sim --features sim-heavy --release → 20 + 20, all green (incl. fuzz_heavy_config_churn, 1000 seeds)
cargo test -p uc2_consensus                          → 67 green (incl. 6 M7-revert tests)
```

### L3: WGL reconfig-churn capstone (the concurrency proof)

`uc2_node/tests/lin_v2.rs::linearizable_under_reconfig_churn` — the same
seeded workers + WGL checker as the failover/purge capstones, with a 4th fault
arm (1-in-4): a spare node cycling `add-learner → promote → demote →
remove-learner` mid-churn, alongside kill-leader / follower-service-crash /
partition-minority+heal. Non-vacuity is asserted (`config_ops_committed ≥ 3`),
not assumed — a run where the config arm barely fires would silently prove
nothing about reconfiguration.

| 0x1107 | 2 | 34 | 12 | 11 | 615 | 98.0% | 97.7 s | Linearizable |
| 0x1107 | 3 | 16 | 4 | 4 | 645 | 99.5% | 44.0 s | Linearizable |

## Review-caught bugs

Evidence the verification stack does its job — three real bugs found and
fixed during M7's authoring, not by inspection but by tests/gate work actually
exercising the mechanism hard enough:

1. **`uc_protocol` MPSC free-space underflow under producer contention**
   (`uc_protocol/src/ring/mpsc.rs`) — a stale `claim_pos` snapshot vs. a
   freshly-reloaded `consumer_pos` could underflow-panic in debug builds under
   sustained multi-producer contention (SPSC has no equivalent window; it has
   exactly one producer). Pre-existing in v2.0, never exercised hard enough to
   surface until the L3 reconfig-churn capstone's spare-node traffic did.
   Fixed with `saturating_sub` (matches the existing outer-call style);
   pinned with a deterministic regression test that forges the exact
   `claim_pos < consumer_pos` shape directly rather than racing threads.
   **Flag for the v2.0.x release notes** — this is a pre-existing bug in
   already-shipped v2.0, found by M7's proof stack, not introduced by M7.
2. **Absence-based halt predicate conflated "not yet admitted" with
   "removed"** (`uc2_consensus::election::ElectionSm::adopt_config`) — the
   original `self_removed` latch fired whenever the JUST-adopted config
   excluded the node's own id, with no way to distinguish a real removal from
   replaying a HISTORICAL config (from before the node joined) during
   catch-up, where a LATER config in the same catch-up run legitimately
   re-includes it. Caught by `resize_3_to_5_to_3` (a second learner
   sequentially and correctly absent from v1/v2, present at v3 — the old
   predicate would have permanently halted it on v1). Fixed by switching to a
   **tombstone-based** predicate (`config.tombstones.contains(&self.id)`) —
   ids are fresh-forever, so absent-and-not-tombstoned unambiguously means
   "not yet admitted."
3. **`publish_peer_band` never cleared trailing cnc peer slots on a SHRINKING
   rebuild** (`uc2_node/src/node.rs`) — found by this Task 11's own gate
   authoring, not by an earlier task. The republish loop only ever wrote
   `0..peer_band.len()`; a rebuild that reduced the peer count (a
   demote/remove-voter/remove-learner) left a stale, uncleared `id_and_role`
   slot at the OLD (now out-of-range) index — surfacing as a ghost duplicate
   entry for a still-live id in `uc2ctl status`'s member listing (and in this
   gate's own peer-band-based catch-up checks). **Diagnostics-only band —
   never gated correctness** (the real membership/quorum state lives in the
   SM's own rebuilt tracker), but a real, user-visible bug in operator-facing
   tooling. Fixed by zeroing every slot from `peer_band.len()..CNC_MAX_PEER_SLOTS`
   whenever the band republishes. Confirmed via `uc2_node/tests/reconfig.rs`
   (unaffected, 10/10 still green — that suite never asserted "no duplicate
   ids", only "the removed id never surfaces again", which is why this
   shipped unnoticed until a stricter check.

**Three real bugs were caught and fixed getting to this PASS** — two in the
orchestrator itself, one a genuine scenario-design gap (not a product bug):

1. **Double `bind_addr()` call** (orchestrator bug) — the address registered
   with the cluster via `uc2ctl add-learner --addr` was computed separately
   from the address actually passed to the spawned node's `--bind` flag;
   `LocalHost.bind_addr()` mints a FRESH ephemeral port on every call, so the
   two calls silently picked DIFFERENT ports. The spare's node process
   started and ran perfectly happily — just never received a single byte of
   replication, because the cluster was sending to a port nothing was
   listening on. Fixed by computing the address once and threading it
   explicitly into both call sites (`start_node_m7` now takes `bind_addr` as
   an explicit parameter rather than calling `host.bind_addr()` itself).
2. **A reused host slot's instance directory was never wiped** (orchestrator
   bug) — `replace-a-box` crashes an original voter, freeing its physical host
   slot for `resize-3-5-3`'s own growth; but the freed slot's directory still
   held the OLD id's durable state (`journal/`, `state/config.state` with the
   old id's own `ConfigRecord`/tombstones). Starting a brand-new id on that
   same directory produced a node stuck at a random half-adopted config
   version — a fresh id must never inherit another id's durable state. Fixed
   with `Host.reset_dir()` (wipe + recreate), called immediately before every
   spare host's node process starts. This exact failure mode is now also
   called out in `docs/ops/uc2-runbook.md` §6's decommission section — it is
   a real operational hazard for a fleet operator "replacing a box" too, not
   just a test-harness artifact.
3. **The gate's own write load could outrun a fresh, far-behind learner's
   catch-up** (scenario-design gap, root-caused, not a product bug) — the
   `m7_gate` reference SM deliberately carries **no snapshot capability**
   (M7's scope is membership, not purge/snapshots), so a learner joining after
   real accumulated backlog can ONLY catch up via NAK/journal replay — a
   throughput-bounded path, unlike M6's near-instant snapshot install for a
   below-floor joiner. A standalone repro measured replay throughput at
   roughly **72 KB/s** on this box, while the unthrottled `loadclient` role
   was sustaining roughly **159 KB/s** — a race the learner can never win, not
   a hang (confirmed directly: stopping the writer let the SAME learner catch
   up completely, just slowly). This surfaced as `resize-3-5-3`'s second
   add-learner never converging within budget. Fixed by pacing
   `m7_gate loadclient`'s writer (`thread::sleep(Duration::from_millis(3))`
   after each committed write, capping it well under the observed replay
   ceiling) — this keeps the scenario a genuine "does a learner catch up
   under REAL concurrent load" proof (M7's actual claim) rather than an
   unrelated replay-throughput benchmark (M5's job). **Worth a maintainer's
   attention**: a production M7 deployment without a `SnapshotStateMachine`
   (or with purge disabled) has the same ceiling — a learner joining far
   behind a sufficiently fast writer may never catch up. M6's snapshot
   capability removes this ceiling entirely (below-floor joins install a
   snapshot instead of replaying), so the practical guidance is: **pair M7
   reconfiguration with M6 snapshots/purge in any deployment with meaningful
   sustained write load**, exactly as the M6 gate doc's own SM already does.

All three are disclosed here rather than silently fixed because they are the
kind of finding the M6 precedent already established this doc records: a bug
that would have produced a false negative (or worse, a false positive from a
broken measurement) on the real fleet run — and, for #3, a real operational
caveat worth stating plainly rather than leaving implicit.
