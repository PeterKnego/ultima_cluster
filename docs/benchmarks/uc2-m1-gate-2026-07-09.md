# uc2 M1 gate — solo append+record+fsync throughput

**Date:** 2026-07-09

> **⚠️ THIS IS A SANDBOX SMOKE / UPPER-BOUND RESULT, NOT THE OFFICIAL M1 GATE.**
>
> This run was taken on a 4-core sandbox whose journal filesystem is a **quota'd
> tmpfs** (`/tmp`, ~840 MiB per-user quota). On tmpfs there is **no writeback I/O
> and `fdatasync` is nearly free**, so the archive's per-block fsync — the whole
> point of the gate — costs almost nothing here. The number below is therefore an
> **upper bound** on what the code path can do when durability is free; it does
> **not** demonstrate the spec §9 bar.
>
> The **official M1 gate** (spec §9: **≥ 1,000,000 msgs/s**, 64 B payloads,
> append + record + **real fdatasync**, solo node) must be run on **c6id NVMe
> fleet hardware**, where fsync has real cost. That run is a follow-up with the
> maintainer (bench-infra has no solo-node role yet) and will be **appended to
> this file** when performed.
>
> A **second local run (Run 2, below) with the journal on real ext4** — the
> sandbox's actual disk, with real writeback and real fdatasync cost — also
> passes, at a **durable (drain-inclusive) rate of 5.66 M msgs/s** (steady-state
> mid-run ~5.79 M msgs/s). Still not the official gate (virtualized disk,
> 4 vCPU), but a far more meaningful local signal than the tmpfs number.
> Note for future local runs: `/tmp` on this box is **tmpfs (RAM-backed)** —
> put journal dirs on ext4 under `/home/claude` instead.

## What the gate measures

Spec §9 / §4: a single node, solo (no replication), appends 64 B messages into
the log buffer while the archive agent block-records them to the journal with one
`fdatasync` per block and advances the durable counter. The metric is sustained
`msgs/s`. The buffer file lives on tmpfs (`/dev/shm` — no writeback); the journal
lives on the "real disk" (here `/tmp`, on the fleet an NVMe volume).

## Host

| | |
|---|---|
| CPU | AMD EPYC-Milan, **4 vCPU** (sandbox) |
| RAM | ~16 GiB |
| Journal FS | **tmpfs** `/tmp`, ~840 MiB per-user quota (fdatasync ~free) |
| Buffer FS | tmpfs `/dev/shm`, 7.6 GiB, no quota |
| Toolchain | rustc 1.96.0, `--release` |

The real gate host (c6id, local NVMe, ext4) is **not** this box.

## Command

The append-only journal grows at the full append rate (~1.26 GB/s here), which
exhausts the ~840 MiB `/tmp` quota in well under one second — so a full 10 s (or
even 5 s) run cannot complete on this box. The run is bounded to 6,000,000
messages (~576 MB of journal, safely under quota) via the optional
`UC2_M1_MAX_MSGS` env cap (unset on the fleet, where the command is exactly the
brief's `... -- <journal_dir> 10`):

```
rm -rf /tmp/uc2-m1-gate && rm -f /dev/shm/uc2-m1-gate.buf
UC2_M1_MAX_MSGS=6000000 \
  cargo run -p uc2_log --release --example m1_gate -- /tmp/uc2-m1-gate 10
```

(Journal dir and `/dev/shm/uc2-m1-gate.buf` are `rm -rf`'d after the run.)

## Output

(This Run 1 output predates the accounting fix — the single `rate` line was
computed with the old method that reads `bytes`/`nblocks` after the drain while
dividing by the append-window `duration`. Here the skew is negligible: **zero
overrun stalls** means the archive kept pace with the appender the whole time,
so there was essentially no backlog to drain and numerator/denominator align.
The number below is still the old-method print format.)

```
== uc2 M1 gate ==
payload            64 B  (96 B framed at 64 B)
duration           0.46 s
appended           6000640 msgs
rate               13167152 msgs/s
recorded+fsynced   576061472 B (1264.0 MB/s)
blocks (=fsyncs)   14732 (32326/s, avg 38 KiB)
overrun stalls     0
GATE (>=1M msgs/s @64B): PASS
```

## Interpretation

- **Rate: ~13.2 M msgs/s**, ~13× the ≥ 1 M/s bar — but with **free tmpfs
  fdatasync**, so read this as an upper bound on the append+record path, not as
  proof of the gate. Zero overrun stalls means the archive kept pace with the
  appender throughout; the ~0.46 s window is the physics of the quota (6 M ×
  96 B ≈ 576 MB fills the budget), not a throughput limit.
- **Structural batching is healthy:** the archive recorded 14,732 blocks
  averaging **38 KiB** each — i.e. ~600 frames coalesced per block, one fsync per
  block, **32 k fsyncs/s** driven by the *block* rate, not the message rate
  (there is no linger anywhere). On real NVMe the fsync cost per block rises and
  the block size grows correspondingly (more frames accumulate per duty cycle),
  which is exactly the group-commit behaviour the gate is meant to exercise — and
  where the real ≥ 1 M/s bar gets tested.
- **What this run does NOT tell us:** the sustained rate once each block fsync
  costs tens of µs on NVMe. That is the whole question the official c6id gate
  answers.

## Run 2 — journal on real ext4 (same box)

Same binary, journal dir moved off tmpfs onto the sandbox's real disk
(`/dev/sda1`, ext4, virtio) under `/home/claude`, so `fdatasync` has real
writeback cost. Bounded to 20 M messages (~1.9 GB journal; 47 GB free):

```
UC2_M1_MAX_MSGS=20000000 \
  cargo run -p uc2_log --release --example m1_gate -- /home/claude/uc2-m1-gate-journal 10
```

```
t=  1s appended=11250342 durable_lag=536870912B
t=  2s appended=17039343 durable_lag=536870912B
== uc2 M1 gate ==
payload            64 B  (96 B framed at 32 B header)
duration (durable) 3.53 s
appended           20000107 msgs
rate (durable)     5660721 msgs/s
append rate (excl. final drain)  7853845 msgs/s
steady-state (mid-run durable delta)  5788842 msgs/s
recorded+fsynced   1920010368 B (543.4 MB/s)
blocks (=fsyncs)   1836 (520/s, avg 1021 KiB)
overrun stalls     63266453
GATE (>=1M msgs/s @64B): PASS
```

> **Accounting correction (supersedes the earlier 6.69 M figure).** An earlier
> revision of this doc reported Run 2 at **6.69 M msgs/s** using burst-inflated
> accounting: the elapsed time was captured when the *append loop* ended, but
> the recorded/fsynced byte totals were read *after* the drain-wait loop — so
> the numerator included the drained backlog whose fsync time was **not** in the
> denominator (a ~34 % skew). The example now captures `elapsed_durable` **after**
> the drain completes and derives the headline **durable rate = appended /
> elapsed_durable**, which is the honest append+record+**fdatasync** number the
> GATE verdict uses. This corrected methodology supersedes the old figure.

Interpretation (headline = the **durable, drain-inclusive** rate):

- **5.66 M msgs/s durable (append + record + real fdatasync)** — 5.7× the
  ≥ 1 M/s bar, on a 4-vCPU virtualized box, with every appended byte fsynced
  before the clock stops. The archive sustains **543 MB/s recorded+fsynced**.
  Two secondary rates confirm the number is honest, not a fill artifact: the
  **append-window rate (excl. final drain) 7.85 M/s** is the unthrottled
  buffer-fill burst (upper bound, backlog not yet durable), and the
  **steady-state mid-run rate 5.79 M/s** — computed from the durable-counter
  delta between the two full-second samples — brackets the headline closely, so
  the sustained fsync-bound regime, not the burst, dominates.
- **Structural batching responded exactly as designed:** with fsync now
  costing real time, blocks grew from 38 KiB (tmpfs) to **~1 MiB (the
  configured max)** and the fsync rate dropped 32 k/s → **520/s**. Same code,
  no linger, no tuning — backlog forms the batch.
- **The overrun gate is doing its job:** `durable_lag` pinned at the full
  512 MiB buffer capacity and 63 M overrun stalls means the appender ran ahead
  to the durability wall and spun there instead of overwriting unrecorded
  bytes. Steady-state throughput is archive-bound (disk-bound), which is the
  correct regime for this gate.
