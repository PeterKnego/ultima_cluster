# Design — uc_autobench distributed-throughput loop on the bench_infra cloud fleet

**Date:** 2026-06-16
**Status:** Design approved; pending spec review → implementation plan.
**Topic:** Wire the `uc_autobench` autoresearch loop to optimize UC's **3-node
distributed throughput ceiling**, using the `bench_infra` cloud fleet as the
per-iteration fitness function (UC-only; no Aeron).

## 1. Motivation

The first valid parity result (task13 §12) measured UC's 3-node sustained throughput
ceiling at **~800 msgs/s** vs Aeron's 20 000/s+ on identical 8-vCPU Hetzner hosts.
task13 §6 identifies UC's submit/apply pipeline as the throughput lever. We want to
attack that ceiling with the existing Claude-Code-driven autoresearch loop
(`uc_autobench`), but measured against **real cross-host hardware** rather than a
local proxy — so wins are trustworthy (the local 4-vCPU box can't even host a clean
3-node run, per §11).

The `bench_infra` rig already provisions a 3-node cloud fleet and runs the UC sweep.
This design connects the two: the loop edits UC source and measures the throughput
gain on a **persistent** cloud fleet each iteration.

## 2. Goals / Non-goals

**Goals**
- Optimize a single metric: UC's **sustained 3-node throughput** (`max(achieved_rate)`
  across the rate ladder), maximize.
- Per-iteration fitness runs on a **persistent** cloud fleet (provision once, keep
  running) — rebuild + UC sweep only, no re-provision, **no Aeron**.
- Never keep a change that breaks SMR correctness: a local lincheck gate runs
  **before** any cloud spend.
- Reuse the existing `uc_autobench` loop model (edit → `run-iter` → keep/discard →
  TSV) and `bench_infra` rig; add the minimum to bridge them.

**Non-goals**
- Aeron is **not** run in this loop (UC-only).
- Not optimizing latency, single-node, or the `uc_protocol` rings (that's the
  `shmem` task's domain).
- Not a fully-automated unattended cloud loop with auto-provision/auto-destroy —
  the human starts the session (fleet up) and ends it (fleet down); the loop assumes
  a live fleet.
- Not changing the parity/comparison methodology (task13).

## 3. Architecture

One-time cloud setup, then a fast inner loop against the live fleet.

```
[once]  make up (aeron_enabled=false)  ──▶  3-node UC-only fleet (CCX33), tuned, UC built
                                              │  (persistent for the session)
[loop]  Claude edits UC source  ─run-iter─▶  ① local cargo build (compile check)
        (submit/apply path)                   ② local lincheck capstone (correctness gate)
                                              ③ make iterate ──▶ rsync+rebuild ×3 → UC 3-node
                                                 sweep on node0 → pull uc_sweep.csv → fitness
                                              ④ JSON {status, uc_throughput_msgs, lincheck_passed}
        keep/discard by fitness  ◀───────────┘   append TSV row
[end]   make destroy
```

- **Fitness metric:** `uc_throughput_msgs = max(achieved_rate)` over the ladder — UC's
  sustained 3-node throughput ceiling. Maximize; KEEP a change only if it beats the
  current best beyond run-to-run noise.
- **Why max achieved_rate:** below the knee achieved≈target; at/above it achieved
  plateaus at the ceiling, so the max over the ladder is the ceiling. `knee_rate` and
  `p99_at_knee_ms` are recorded as secondary/observability, not gated.
- **Real signal, no proxy gap:** every iteration measures on the same 8-vCPU
  cross-host fleet the parity result used — no local-loopback fidelity loss.

## 4. bench_infra changes

**(a) UC-only mode** — new group_var `aeron_enabled: false` (default keeps current
behavior `true` for the parity flow):
- Provision: `build_aeron` role is skipped when false (no clone / `deployTar`).
- Run role: the Aeron start/sweep/stop tasks are skipped when false; only the UC
  path runs.

**(b) `make iterate` target** — the per-loop operation against the **live** fleet
(inventory already generated by `make up`):
1. `build_uc` role re-run: `rsync` UC working tree (+ `ultima_db` sibling) to the 3
   hosts, incremental `cargo build --release`.
2. UC-only run: start the 3-node UC cluster, drive `commit-path-load` ladder from
   node0, tear down.
3. `collect`: pull `uc_sweep.csv`.
4. Print one JSON line to stdout: `{"uc_throughput_msgs": <max achieved_rate>,
   "knee_rate": <…>, "p99_at_knee_ms": <…>}`.

No re-provision (toolchains/os_tune unchanged); no Aeron. Implemented as a thin
playbook (`iterate.yml` = `build_uc` + UC-only `run` + `collect`) plus a small
fitness-extraction step that parses the pulled CSV.

## 5. uc_autobench task `uc-throughput`

**(a) `tasks/uc-throughput/program.md`** overlay declares:
- **Mutable paths** (the throughput lever, task13 §6): `uc_node` client_dispatcher +
  apply-ring publish/enqueue, the ring wakeup path, and the openraft `Config` knobs in
  `uc_node/src/runtime/builder.rs` (`api_batch_capacity`, `max_payload_entries`,
  `api_batch_linger_ms`). Excludes `uc_protocol` rings.
- **Primary metric** `uc_throughput_msgs` (maximize). KEEP iff it beats the current
  best beyond noise AND the lincheck gate passed.
- **Correctness gate:** the lincheck capstone (`linearizable_under_failover`).
- **Special instructions:** the persistent fleet must be up (`make up` with
  `aeron_enabled=false`) before the loop starts; the loop assumes it. Noise: cloud
  `achieved_rate` run-to-run variance — compare beyond ~5%.

**(b) `tasks/uc-throughput/results.tsv`** header:
`commit  uc_throughput_msgs  knee_rate  p99_at_knee_ms  lincheck_passed  status  description`

**(c) `run-iter --task uc-throughput`** — ordering is **cheap-gate-first, expensive-
fitness-last** (inverted vs `shmem`, because here the cloud sweep is the truth, not a
Goodhart gate):
1. **Local compile check** — `cargo build -p uc_autobench --bin uc-node-launch --bin
   commit-path-load`. Fail → `status=build_failed`, discard (no cloud spend).
2. **Correctness gate (local, ~40 s)** — `cargo test -p uc_node --test lin_register
   linearizable_under_failover -- --test-threads=1`. Fail → `status=lincheck_failed`,
   discard. A throughput win that breaks linearizability never reaches the cloud.
3. **Fitness (cloud, ~5–10 min)** — `make iterate` against the live fleet; parse
   `uc_throughput_msgs` from its JSON.
4. Emit JSON `{status, stage, metrics:{uc_throughput_msgs, knee_rate, p99_at_knee_ms},
   gate:{lincheck_passed}}`. Map to TSV: `pass`+improved → keep; `pass`+no-improve →
   discard; gate/build fail → discard (crash only on harness breakage).

**Loop (Claude-driven):** read the overlay → ensure fleet up → {edit a mutable file →
`run-iter --task uc-throughput` → keep (commit) or discard (revert) → append TSV} →
repeat → `make destroy` at session end.

## 6. Lifecycle, cost & guardrails

- **Cost:** persistent fleet ~€0.24/hr (3× CCX33) for the session, flat; each
  iteration adds no provision cost. A tuning session of N iters ≈ N × (~5–10 min) of
  fleet time. The `make status` TTL guard (bench_infra) still applies; the loop should
  `make destroy` when the human stops.
- **Correctness:** the lincheck capstone gate (step 2) is the floor — runs every
  iteration, before cloud spend; no variant that breaks SMR correctness is kept or
  even measured on the cloud.
- **Goodhart:** the fitness is the real cloud bench and `commit-path-load` measures
  real committed throughput, so there is no microbench-proxy to exploit. The only
  failure mode (faster-but-incorrect) is gated locally.
- **Fleet reuse across iterations:** the `run` role already cleans stale cluster state
  at start (cleanup task), so repeated `make iterate` runs are idempotent on the same
  hosts.

## 7. Success criteria

1. `make up` with `aeron_enabled=false` brings up a UC-only fleet (no aeron build).
2. `make iterate` on the live fleet rebuilds UC from the local working tree, runs the
   UC sweep, and prints a valid `uc_throughput_msgs` JSON in ~5–10 min, idempotently
   re-runnable.
3. `run-iter --task uc-throughput` returns `build_failed` / `lincheck_failed` without
   cloud spend when those gates fail, and a real `uc_throughput_msgs` when they pass.
4. A deliberate throughput-neutral edit shows no fitness change beyond noise; a
   deliberate correctness-breaking edit is caught by the lincheck gate (discarded,
   no cloud run).
5. The loop can run unattended (no questions/pauses) keeping/discarding by the metric,
   appending TSV rows, until the human stops it.

## 8. Out of scope / future

- Auto-provision/auto-destroy of the fleet inside the loop (human-managed for now).
- Latency-targeted optimization; non-durable posture sweeps.
- Optimizing the `ultima_db`/journal layers (separate autobench tasks already exist).
- Finding Aeron's knee / re-running the parity comparison (task13).
