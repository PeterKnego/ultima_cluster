## What the gate measures

Spec: `docs/superpowers/specs/2026-08-19-uc2-production-readiness-design.md`
§6 (M11), §1 (locked decisions), §3 (non-goals).
Plan: `docs/superpowers/plans/2026-08-20-uc2-m11-survivable-cluster.md`.

M11 makes the cluster **survivable**: an operator can back up a node under
load and restore it onto a new host (proven as a CI test, not a documented
procedure), force a survivor out of quorum loss with the data-loss window
stated instead of hidden, watch the disk-space wall before hitting it and
prove `ENOSPC` is a genuine asserted fail-stop rather than a silent
corruption risk, and execute a flag-day upgrade with a measured downtime
number. M11 changes no consensus or wire-protocol surface and touches the
cnc page only in the already-reserved free band (`CNC_OFF_FREE_DISK_BYTES =
3840`, pinned in both `uc_protocol` and `uc_log`). That is why this gate
measures **recovery completeness and honesty under real destructive
scenarios** (does a restored host actually converge with zero acked-write
loss; does a forced quorum-loss recovery tell the truth about its narrower
loss window; does the fail-stop chain really fire end-to-end from a real
`EACCES`/`ENOSPC`; is the operator warned before the wall, not just after it),
not consensus safety — that continues to be held by the sim, the lincheck
capstones, the crashtest, and the Lean proofs, none of which this milestone
touches.

### Why each row is the right bar

**Row 1 — the spec's acceptance sentence, literally.** "A node is backed up
under load, its host destroyed, a new host restored from the backup alone,
and it rejoins and converges" is the whole point of Task 1-3; a test that
merely checks `backup_instance`/`restore_artifact` in isolation could pass
while the real multi-process, real-SIGKILL, real-`rm -rf` version still
fails. 3/3 consecutive (not 1/1) catches a flake the way M9/M10's repeated
local runs did. The straddle anti-vacuity test is the other half: a backup
tool that never notices a broken copy order is worse than no verify at all,
so `verify_artifact` must actually call a deliberately-broken artifact a
`Hole`, not just pass every artifact handed to it.

**Row 2 — honesty about the loss window is the property, not just recovery.**
`force_single_member` is a real data-loss operation (2-of-3 permanently
gone); the bar is not "the survivor comes back" alone but that it comes back
holding **exactly** what it durably had — no more (nothing invented), no
less (nothing silently dropped from what it already held) — while the
narrower "old-quorum-acked-but-never-replicated-here" loss is printed, not
hidden. The repair tail (fresh learner rejoin + promote) proves the forced
cluster is a normal, live, growable cluster afterward, not a dead end.

**Row 3a/3b — the fail-stop chain is real product code, proven end to end,
twice, at two different errnos.** The as-built anchor (journal writer halt →
`ArchiveError` → `archive.do_work(...).expect("archive fail-stop")` →
`agent_failstopped` → daemon exit 1) already exists; what these rows prove is
that it actually fires from a genuinely full/permission-denied filesystem,
that the two survivors keep serving without the third, and that the daemon
rejoins cleanly once the condition clears. The product's fail-stop is
errno-agnostic (ANY journal write/fsync `io::Error` halts it), so 3a's
`EACCES` evidence is genuine evidence for 3b's `ENOSPC` chain, not a
simulation of it — but only 3b carries the `ENOSPC` errno itself in the
panic text, which is why both are gated and neither substitutes for the
other.

**Row 4 — an alert that has never fired is documentation, and a warning that
never renders is silence.** `uc2_free_disk_bytes` exists so an operator sees
the wall coming before `ENOSPC` hits it; a family that deserializes correctly
in unit tests but never actually appears in a live daemon's real HTTP scrape
is a broken promise no code review catches. The YAML↔builders cross-check
anti-vacuity step exists for the identical reason M10's per-peer-occupied and
non-vacuous-window checks exist elsewhere in this project: a check that can
never fail is not a check. Removing a builder and watching the script name
it, then restoring and reverifying green, is the executable proof that the
completeness cross-check is load-bearing rather than decorative.

**Row 5 — the M9/M10 pattern: cross-host cost is a fleet-only claim.** A
flag-day upgrade's downtime is dominated by real network RTT (ssh, election
timeout propagation across hosts) that one dev-box process cannot honestly
produce, exactly the reasoning that made M9's row 3 and M10's rows 2/3
fleet-adjudicated. The 60 s bar (versus M9's 15 s single-restart bar) reflects
a whole-cluster stop/upgrade/start cycle across every node, not one node's
restart.

## Honest-failure protocol

Adopted verbatim from M7/M9/M10:

- The gate binary prints the bar and `exit(1)` on FAIL. A green terminal is
  not a PASS; the exit code is.
- Bar and result are recorded in separate commits, bar first (this document,
  before the harness).
- A FAIL is diagnosed before it is re-run. Harness defects and genuine
  properties are separated and both recorded.
- Row 5 (and row 3b outside CI/a fixture run) is not locally adjudicable;
  local numbers, where printed at all, are smoke, never the gate.
- `v2.5.0` tags only when row 5 passes on a real fleet — a separate,
  user-approved step, not performed by this document or by landing this
  branch.

## Two findings recorded here — the biggest actual catches of this milestone

Beyond the plan's four tasks, building and hardening the backup/restore path
(Task 1-3) surfaced two real, pre-existing `uc_journal` defects that no
earlier milestone's proof stack (sim, lincheck, crashtest, Lean) had reason to
exercise — none of them involve multiple appenders or concurrent readers, the
kind of interleaving the existing proof stack is built to explore; both are
about a single serial journal writer's own crash-recovery and rotation
bookkeeping.

- **Crash-torn-tail boot refusal, and the heal-residue wedge chain it then
  exposed.** `Journal::open`'s strict `scan()` used to hard-refuse to boot on
  an active segment whose last record's length prefix landed but whose
  body/CRC were still preallocated zero-fill — a real `kill -9` interleaving,
  and exactly the state `TailReader::scan_tolerant` already classified as a
  torn tail everywhere else. Fixed to heal through the existing torn-tail
  machinery (commit `1ee907e`). Three follow-on fix rounds closed a wedge
  chain the heal itself created: the heal's `reset_cursor()` only rewound the
  *logical* cursor, leaving real residue physically on disk for a later
  strict re-scan to CRC-fail on again, permanently, on every subsequent boot
  (commit `d502935`); the re-zero was capped at `segment_size_bytes` even
  though a straddling last record can legitimately push a segment's true
  physical size past that (commit `7f690bc`); and `active_segment_dirty`
  could go stale-true against an emptied segment list, panicking (and
  poisoning the mutex) on the very next append (commit `7ba74e8`). Code:
  `uc_journal/src/journal/mod.rs` (open/heal), `uc_journal/src/journal/writer.rs`
  (seal/dirty-flag bookkeeping).
- **The masked roll-fsync acked-durability hole.** `write_batch`'s segment
  rotation fsynced only `segments.last()` (the NEW segment) after a roll,
  never the segment the just-written run actually landed in — every request
  in that batch was acked `Ok` on the strength of an `fdatasync` of a
  *different file*. An empirical probe demonstrated it directly: 120 records
  into 4 KiB segments, pipelined, straddled 1-2 rolls per trial with all 120
  `Notifier`s returning `Ok`, and traced 47 acked records that never once
  appeared as an fsync target. It was masked in `ultima_cluster` today only
  because the archive journal has exactly one, strictly-serial appender — an
  emergent property of one caller, not a contract. Fixed with fsync-on-seal,
  gated on a persistent `active_segment_dirty` flag so both the intra-batch
  straddle AND the `Durability::Eventual` cross-batch variant close (commit
  `8f9268c`). Code: `uc_journal/src/journal/writer.rs` (`write_batch`'s
  `need_new` branch).

### 2026-08-20 correction (fix round 1)

A post-commit review of the run above found two problems, both fixed in the
fix-round commit that follows this amendment. Recorded here per this
document's own honest-failure protocol, rather than silently edited away.

1. **Critical (empirically reproduced by the review): a `SIGTERM` to the gate
   process during row 4's anti-vacuity trip left `scripts/m10_alert_fire.sh`
   corrupted in the working tree.** The original `check_yaml_builders_anti_vacuity`
   mutated the real tracked file in place and relied on a `Drop` guard to
   restore it on the way back out — but `Drop` does not run on an unhandled
   signal (`SIGTERM`'s default disposition kills the process immediately, no
   unwind), and the mutated-file window was the ENTIRE ~80s
   `m10_alert_fire.sh` invocation (the trip run itself), not the "~1-2s"
   the fix's own task report claimed. **Fixed**: the anti-vacuity probe now
   runs entirely against a scratch copy of the script
   (`uc_node/examples/m11_gate.rs`'s `check_yaml_builders_anti_vacuity`),
   with its `ROOT=` line hardcoded to this process's own real repo root
   instead of the original `dirname($0)/..` derivation — verified
   empirically sufficient for both of the script's `$ROOT`-relative path
   uses (`RULES_FILE`, the `cargo run --manifest-path` invocation), so
   `scripts/m10_alert_fire.sh` is never opened for writing at any point,
   under any exit path, including a signal. The pre-mutation baseline
   assertion (confirming the tracked file still contains the expected
   `RULE_BUILDERS` entry before building the scratch copy) is kept as a
   tripwire against a previously-corrupted tree — a real, if partial,
   mitigation the original design also had.
2. **Bar-integrity violation: the results-commit (`0ecb77c`) edited the
   row-4 BAR CELL itself** — from its pre-committed `6af0f31` wording ("...
   the script is restored and re-verified green") to "... the script is
   restored byte-for-byte" — to match what that commit's (now-superseded)
   harness design actually did. That is precisely the "edit the bar to
   match a result" move this document's own honest-failure protocol
   forbids. That commit's self-review described the change as prose-only;
   that description was wrong — the diff touched the bar table cell itself,
   not only the surrounding "why row 4" paragraph (which was also edited,
   and is likewise reverted here). **Corrected**: both the bar cell and the
   "why row 4" paragraph above are reverted to their exact `6af0f31`
   wording (byte-diffed against that commit to confirm). With the
   scratch-copy redesign, the bar's "restored and re-verified green" clause
   is now satisfied **by construction**: the tracked script is never
   mutated at all, so it stays green throughout row 4 without any restore
   step being needed; "re-verified" is the normal (unmutated)
   `scripts/m10_alert_fire.sh` invocation that already runs earlier in row
   4, on every gate run.

The original run's row-4 result (PASS) stood correctly on its own terms —

### Topology deviation, and why (recorded, not smoothed over)

The intended fleet was 5 hosts. It ran on **4 × `c6id.xlarge`**, because of
two independent AWS-side constraints hit during bring-up:

1. **The account's us-east-1 on-demand Standard vCPU limit is 32.** 5 ×
   `c6id.2xlarge` is 40 vCPU: the first apply left two instances
   running-but-unreachable and an explicit replace failed outright with
   `VcpuLimitExceeded`. `terraform.tfvars` was moved to `c6id.xlarge`
   (5 × 4 = 20 vCPU, inside the limit) with the reason recorded in-file.
   Row 5 measures DOWNTIME (ssh fan-out, systemd stop/start, election
   timeouts), not per-host throughput, so the smaller host does not weaken
   the bar — but any THROUGHPUT gate (M5/M6 A/B) must restore
   `c6id.2xlarge`.
2. **Three consecutive instances in one slot came up with no networking** —
   unreachable on port 22 from this box AND un-pingable from a healthy peer
   inside the VPC, i.e. instance-side, not a security-group or SSH-path
   problem. After the third failure the row was run on the four healthy

### What actually happens when the filesystem is full

Three different outcomes across runs, none of them the bar's "named
fail-stop (`ErrorKind::StorageFull`, `os error 28`), exit 1":

1. **The daemon dies by signal, not exit code.** Instrumented run:
   `node0 exit: code=None signal=Some(7) core=true`, with `df` showing 100%
   full at the moment of exit, and node 0's stderr containing NO
   `agent_failstopped` line. Signal 7 is `SIGBUS`.
2. **The test/client process dies by SIGBUS instead**: `process didn't exit
   successfully: enospc-... (signal: 7, SIGBUS: access to undefined memory)`.
3. **Nothing dies and the cluster wedges**: disk at 0 free, node 0 alive for
   the full 60 s, no fail-stop marker, load client looping on
   `request timed out after 1.5s -- reconnecting`. Explained by (2): once
   whichever process was making progress is gone, appends stop, so the
   journal never needs a new segment and the node never sees an I/O error at
   all.

### Root cause

Every mmapped file in an instance dir is **deliberately sparse**.
`uc_protocol::ring::create_shared_backing_file` (`uc_protocol/src/ring/common.rs:356`)
does `set_len(len)` followed by `fallocate(FALLOC_FL_PUNCH_HOLE |
FALLOC_FL_KEEP_SIZE)` — its own comment says "a 256 MiB buffer stays sparse".
Measured on the fixture after a run (apparent size vs. allocated bytes):

```
 4194560       4096   egress_node.broadcast
 4194560      40960   ingress.ring
 1048576      81920   log.buf
```

A write into an unallocated page of such a mapping must allocate a block at
PAGE-FAULT time. On a full filesystem that allocation fails, and the kernel
raises `SIGBUS` — which is not an `io::Error`, cannot be returned by any
Rust call, and kills the process outright. The journal writer's
halt-on-error path (`uc_journal/src/journal/writer.rs`, `halt_writer`)
is never reached, so the whole documented chain — journal halt →
`ArchiveError` → `archive fail-stop` panic → `agent_failstopped` → exit 1 —
is bypassed. Whichever process (node, service, or client — they all map
these files) touches an unmaterialized page first is the one that dies,
which is why the observed outcome varies run to run.

Row 3a's `EACCES` evidence remains valid and remains different: `chmod 0555`
makes a segment *create* fail, which IS an `io::Error` on the journal path,
so that run exercises the real chain. `ENOSPC` differs precisely because it
can arrive through the mmap rather than through a syscall return value.

### What this does and does not imply

- **The test is now right and the product is wrong** (or the bar is wrong).
  The bar was pre-committed and stays as written; this run says the shipped
  behaviour does not meet it.
- This run produced **no evidence of acked-write loss** — the failure is
  that the disk wall is met by process death (or a silent wedge) rather than
  by a named, logged fail-stop. An operator gets a `SIGBUS` core dump, or a
  cluster that stops answering, instead of the M11 story.
- M10's `free_disk_bytes` + `Uc2DiskLow` (row 4, PASS) are the mitigation
  that still works: they warn BEFORE the wall. What M11 claims and does not
  yet deliver is a clean landing AT the wall.

### Not fixed here

The fix is a product change with a real cost, and a design decision rather
than a test tweak. The options, for the record:

1. **Allocate real blocks for the mmapped files** (`fallocate` without
   `PUNCH_HOLE`, or `FALLOC_FL_ZERO_RANGE`) so `ENOSPC` surfaces as a clean
   error at CREATE time and no later page fault can find an unbacked page.
   Costs the sparseness the current code deliberately keeps: a 256 MiB
   default log buffer would occupy 256 MiB on disk.
2. **Install a `SIGBUS` handler** that converts a fault inside a known
   mapping into a fail-stop. Async-signal-safety makes this delicate, and it
   converts a hard kill into a controlled one rather than preventing it.
3. **Refuse to start / stop accepting writes above a free-space floor**,
   using M10's existing `free_disk_bytes`. A mitigation, not a fix: it
   narrows the window rather than closing it.

Until one lands, row 3b stays **FAIL** and `v2.5.0` does not tag.

## Row 3b amendment 3 — PASS, after fixing the product (2026-08-21)

Row 3b now passes end to end against a genuine loopback fixture:

```
test enospc_fails_stops_asserted_and_the_cluster_survives ... ok
test write_denied_drives_the_same_failstop_chain ... ok
test result: ok. 2 passed; 0 failed
```

The bar is met as written: a named fail-stop (`StorageFull` / `os error 28`),
daemon exit 1, the two survivors keep committing throughout, and node 0
rejoins and converges once space is returned.

Three changes were needed, in the order the evidence demanded them.

**1. `uc_protocol::ring::create_shared_backing_file`: `PUNCH_HOLE` →
`ZERO_RANGE`.** The root cause from amendment 2. Punching holes zeroes the
file and keeps it sparse; `ZERO_RANGE` zeroes it and RESERVES the blocks, as
unwritten extents, so no later page fault can need an allocation that a full
disk cannot satisfy. `ENOSPC` now surfaces where it can be handled — as an
`io::Error` returned by `fallocate` at CREATE time — instead of as a `SIGBUS`
that kills a running process. This is the same answer Aeron reaches, from the
same constraint: Aeron makes sparseness a config knob
(`aeron.term.buffer.sparse.file`, "can save space at the expense of latency")
and enables storage checks by default (`aeron.perform.storage.checks` →
`FileStoreLogFactory.checkStorage`, "insufficient usable storage for new log
of length=..."). `fallocate` is the stronger form of that check: Aeron's is
look-then-leap and races, while the reservation either succeeds or reports
`ENOSPC` atomically.

**Cost, stated plainly:** these files are no longer sparse. A default
instance dir reserves ~78 MiB at startup (64 MiB log buffer + ~14 MiB of IPC
rings) instead of materializing lazily, and a node that cannot reserve it
refuses to start with a named error. `packaging/node.example.toml` documents
this where operators will meet it.

**2. `uc_journal`'s segment preallocator stopped discarding the errno.**
With the SIGBUS gone, the chain fired correctly — `uc2-archive` panic →
`agent_failstopped` → exit 1 — but the operator-visible text was
`Journal(Io(Custom { kind: Other, error: "segment preallocation failed" }))`.
`prealloc_failed()` substituted a flat string for the real `io::Error`, so a
full disk fail-stopped the node without ever saying the disk was full. The
failing error's kind and errno are now captured and rebuilt for each waiter,
which is what puts `StorageFull` and `os error 28` in front of the operator.
This was a latent defect for EVERY preallocation errno, not just `ENOSPC`.

**3. `scripts/enospc_fixture.sh`: headroom default 8 MiB → 24 MiB.** A
consequence of (1): with blocks actually reserved, a node needs ~15 MiB free
just to start in the test's small-buffer configuration, and against the old
margin it refused to boot at all ("failed to start node 0: io: No space left
on device") — which tests the startup refusal, not the under-load wall. The
margin now leaves room to boot and warm up; the test's own
`squeeze_free_space` takes the space away when it wants the wall. The same
script's `chown` was also fixed to honour `SUDO_UID`/`SUDO_GID`: run as
`sudo enospc_fixture.sh create ...` it had been chowning the mount back to
root, leaving the daemon unable to create its instance dir.
