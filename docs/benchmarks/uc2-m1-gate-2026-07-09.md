# uc2 M1 gate — solo append+record+fsync throughput

**Date:** 2026-07-09

> **⚠️ THIS IS A SANDBOX SMOKE / UPPER-BOUND RESULT, NOT THE OFFICIAL M1 GATE.**
>
> This run was taken on a 4-core sandbox whose journal filesystem is a **quota'd
> tmpfs** (`/tmp`, ~840 MiB per-user quota). On tmpfs there is **no writeback I/O
> and `fdatasync` is nearly free**, so the archive's per-block fsync — the whole
> point of the gate — costs almost nothing here. The number below is therefore an
> **upper bound** on what the code path can do when durability is free; it does
> **not** demonstrate the spec §9 bar.
>
> The **official M1 gate** (spec §9: **≥ 1,000,000 msgs/s**, 64 B payloads,
> append + record + **real fdatasync**, solo node) must be run on **c6id NVMe
> fleet hardware**, where fsync has real cost. That run is a follow-up with the
> maintainer (bench-infra has no solo-node role yet) and will be **appended to
> this file** when performed.

## What the gate measures

Spec §9 / §4: a single node, solo (no replication), appends 64 B messages into
the log buffer while the archive agent block-records them to the journal with one
`fdatasync` per block and advances the durable counter. The metric is sustained
`msgs/s`. The buffer file lives on tmpfs (`/dev/shm` — no writeback); the journal
lives on the "real disk" (here `/tmp`, on the fleet an NVMe volume).

## Host

| | |
|---|---|
| CPU | AMD EPYC-Milan, **4 vCPU** (sandbox) |
| RAM | ~16 GiB |
| Journal FS | **tmpfs** `/tmp`, ~840 MiB per-user quota (fdatasync ~free) |
| Buffer FS | tmpfs `/dev/shm`, 7.6 GiB, no quota |
| Toolchain | rustc 1.96.0, `--release` |

The real gate host (c6id, local NVMe, ext4) is **not** this box.

## Command

The append-only journal grows at the full append rate (~1.26 GB/s here), which
exhausts the ~840 MiB `/tmp` quota in well under one second — so a full 10 s (or
even 5 s) run cannot complete on this box. The run is bounded to 6,000,000
messages (~576 MB of journal, safely under quota) via the optional
`UC2_M1_MAX_MSGS` env cap (unset on the fleet, where the command is exactly the
brief's `... -- <journal_dir> 10`):

```
rm -rf /tmp/uc2-m1-gate && rm -f /dev/shm/uc2-m1-gate.buf
UC2_M1_MAX_MSGS=6000000 \
  cargo run -p uc2_log --release --example m1_gate -- /tmp/uc2-m1-gate 10
```

(Journal dir and `/dev/shm/uc2-m1-gate.buf` are `rm -rf`'d after the run.)

## Output

```
== uc2 M1 gate ==
payload            64 B  (96 B framed at 64 B)
duration           0.46 s
appended           6000640 msgs
rate               13167152 msgs/s
recorded+fsynced   576061472 B (1264.0 MB/s)
blocks (=fsyncs)   14732 (32326/s, avg 38 KiB)
overrun stalls     0
GATE (>=1M msgs/s @64B): PASS
```

## Interpretation

- **Rate: ~13.2 M msgs/s**, ~13× the ≥ 1 M/s bar — but with **free tmpfs
  fdatasync**, so read this as an upper bound on the append+record path, not as
  proof of the gate. Zero overrun stalls means the archive kept pace with the
  appender throughout; the ~0.46 s window is the physics of the quota (6 M ×
  96 B ≈ 576 MB fills the budget), not a throughput limit.
- **Structural batching is healthy:** the archive recorded 14,732 blocks
  averaging **38 KiB** each — i.e. ~600 frames coalesced per block, one fsync per
  block, **32 k fsyncs/s** driven by the *block* rate, not the message rate
  (there is no linger anywhere). On real NVMe the fsync cost per block rises and
  the block size grows correspondingly (more frames accumulate per duty cycle),
  which is exactly the group-commit behaviour the gate is meant to exercise — and
  where the real ≥ 1 M/s bar gets tested.
- **What this run does NOT tell us:** the sustained rate once each block fsync
  costs tens of µs on NVMe. That is the whole question the official c6id gate
  answers.
