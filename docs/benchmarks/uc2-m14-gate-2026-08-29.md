## What the gate measures

Spec: §1–§9 (the design), §14 (as built), **§15 (this gate)**. M14 puts N
state-machine processes behind one log: a bounded lag barrier or lockstep
between them (M14a), per-FSM query routing and a client fan-in (M14b), a
snapshot session that ships one artifact per declared FSM on wire `0.6.0`
(M14c), and per-FSM observability (M14c). Local numbers exist
(`uc2-m14a-apply-hop-2026-08-27.md`, `uc2-m14c-client-hop-2026-08-28.md`)
and set no bar; this is where the rates are adjudicated.

**Coverage statement (spec §15.1).** `2.8.0` ships multi-service with unit
tests, in-process integration on one node and a 3-node cluster, the M14b sim
scenario and the fuzz seeds. The two-FSM linearizability, partition,
hard-crash and Elle capstones are **M14c2**, a proof-only `2.8.1` after this
release. This gate's rows are what only a fleet can measure; they are not a
substitute for those capstones and do not claim to be.
**Closed by `2.8.1` (2026-08-30): see [VERIFICATION §11](../VERIFICATION.md#11-what-is-not-verified)**
for the seven two-FSM capstones, the Elle two-FSM pass and what remains open
(row e was not re-measured; the pinned rig has not run on a fleet).

### Reading the rules

**Rate** is the direct `Engine` client's completed operations per second over
the middle 8 s of a 12 s arm (2 s warm-up, 2 s tail), `--inflight 4096`,
64-byte payload, session envelope on, fan-in (`try_submit_all`) whenever two
FSMs are declared — one completion = every declared FSM answered. The client
runs **on the leader host** (shmem-attached; spec §15.2 errata). Rows a–e use
M13's voter shape, so row a's N=1 number is measured on the same host shape as
M13's direct arm; the client binary and its windowing changed since, so the
M13 number is context, not a bar (CLAUDE.md's same-source-rebuild lesson).

**`K`** is chosen by a calibration ladder run first (`SpinCountSm(K)` alone
at K ∈ {250 … 8000}, 12 s each): the K whose rate is nearest 0.5 × `n1`.
Row b compares `pair` against `slow1` **at that same K in the same run**, so
the bar is independent of where the calibration lands. Both numbers and the
ladder are recorded below.

**Row d** is M9's rule (`m9_fleet_gate.py:343-379`), read from the client's
own per-second timeline on the same host as the kill (no clock skew): baseline
= mean over seconds [2, 10) of the arm; t0 is taken before the SIGKILL ssh;
recovered = the end of the first 2 s window at ≥ 80 % of baseline, confirmed
by the next 2 s window also qualifying. The driver evaluates that rule over
overlapping 2 s windows stepped 1 s at a time, where M9 stepped
non-overlapping 2 s windows; a finer step can only find an EARLIER qualifying
window, never a later one, so it errs toward a *smaller* recovery time — the
confirmation requirement (the next window must qualify too) is unchanged. The
second clause polls `uc2ctl status` on that host for `id=1 attached=true`
with an incarnation strictly above the pre-kill reading (the SIGKILLed
service leaves its `attached` bit set, so the bit alone is the corpse's, not
the new life's) and `lag ≤ fsm_lag`.

**Row d's procedure was re-specified on 2026-08-29, after run 1** (the bar was
not): the arm now runs with a 32 MiB snapshot policy on **both** FSMs **and
with purge on** (`PurgePolicy::BelowSnapshot`, 16 MiB journal segments — row
f's shape), so the restarted FSM 1 installs its newest artifact and
tail-replays instead of walking the whole journal; and the measuring client
submits to **FSM 0 only** instead of fan-in. Both halves of the first change
are load-bearing, and the purge is the half that does the work: reconstruction
enters the install branch only inside the gap guard `if first > start_pos`
(`uc_service/src/replay.rs:73-78`), where `first` is the base position of the
oldest *retained* journal segment — 0 while nothing has been purged — and a
fresh process's `start_pos` is 0 (`uc_service/src/attach.rs:153`), so with
purge off `0 > 0` is false and a snapshot policy alone shortens nothing; only
`PurgePolicy::BelowSnapshot` dispatches `ArchiveCmd::Purge` and lifts `first`
(`uc_node/src/node.rs:3261-3270`). The second change's reason is that run 1's
rate clause measured a timeout, not a recovery: journal replay is
publish-silent (`uc_service/src/replay.rs:44-46`), so every in-flight fan-in
request could retire only on the client's 30 s `request_timeout`, pinning the
rate at 0 for the rest of the arm no matter how fast FSM 1 recovered.
Submitting to FSM 0 alone keeps the recovery clock the row wants, because FSM
0's apply is held back by the bounded 64 MiB lag barrier while FSM 1 is dead
and resumes exactly when FSM 1 has caught up.

**Row f**: the voters run `PurgePolicy::BelowSnapshot { slack_bytes: 0 }`
with 16 MiB journal segments and a 32 MiB snapshot interval
(`M14_SEGMENT_BYTES` / `M14_SNAPSHOT_INTERVAL_BYTES`; at the direct client's
~100 MB/s a 90 s arm still rolls the journal ~500 times and builds ~250
snapshots), so the joiner is below the floor and converges by a snapshot
session — two artifacts (`SNAP_BEGIN_LAYOUT_V2`, `services_declared = 0b11`).
"Joined" = both FSMs attached on the learner with `applied ≥` the leader's
per-id `applied` at `add-learner` time and `snapshot_pos > 0`, **and at least
one `snapshot_installed` record in the learner's node log** — without that
last clause the criterion is also met by a learner that caught up by plain
journal replay and built its own snapshots, which would prove nothing about
the wire-0.6.0 session. The install clause was added on 2026-08-29 before the
first run, as a strengthening (a learner can also converge by journal replay,
which would not exercise the 0.6.0 stream). The refusal pair is the node role's
`snap_refusals=(a,b)` stats line (`Node::snapshot_session_refusals`).

## Honest-failure protocol

Adopted verbatim from M7/M9/M10/M11/M12/M13: the driver prints the bar and
exits non-zero on any FAIL — a green terminal is not a PASS; the exit code
is. Bar and result land in separate commits, bar first. A FAIL is diagnosed
before any re-run; harness defects and genuine product properties are both
recorded. Rows c and f's refusal clause are consensus/wire defects and block
the release outright. A row f miss is diagnosed against the journal/snapshot
sizing first — `M14_SEGMENT_BYTES` and `M14_SNAPSHOT_INTERVAL_BYTES` in the
driver — before it is called a product defect: harness before product.
Tagging `v2.8.0` is a separate user-approved step.

#### What the two attach/detach pairs mean (FACT, from the code)

`uc_node/src/node.rs:2870-2911` (`note_service_transitions`) emits
`service_attached` on an **epoch bump** and `service_detached` only when a
**non-live duty cycle is actually observed**, where live = the slot's ATTACHED
bit set *and* its heartbeat fresher than `SERVICE_STALE_NS = 3 s`
(`uc_node/src/services.rs:220`). The attach arm sets `service_was_live = true`
unconditionally on the epoch bump; if the very next duty cycle finds the slot
not live, `service_detached` fires immediately. That is exactly the 12 µs pairs
at boot (records 1-2 and 3-4): the epoch is bumped inside
`uc_service::attach` — `uc_service/src/attach.rs:157-162`, incarnation then
epoch, a few instructions apart — *before* the apply thread exists and
therefore before any heartbeat has been stamped, so the consensus agent's next
busy-spin cycle sees "attached bit set, heartbeat never" and reports a
departure microseconds after the arrival. **This is a labelling artefact of a
correct rule, not an event**; it is exactly the asymmetry the function's own
doc comment warns about.

The consequence that matters for row d: **there is no "became live" record.**
The code has an attach arm (epoch bump) and a detach arm (non-live observed),
and nothing that fires when a non-live slot becomes live again without an epoch
bump. So the node's transition log can tell you when the restarted FSM
*arrived* and never when it became *useful*.

#### (i) Harness — FACT

The restarted FSM had **no snapshot policy**, so it rebuilt by replaying the
whole journal.

- `bench-infra/scripts/m14_fleet_gate.py:527` restarts the killed unit with
  `service_args(h, 1, K, 0)`; `service_args` (line 288-293) appends
  `--snapshot-interval-bytes` **only when `snap` is truthy**, and it is `0`
  here. The original launch was the same: `arm_kill` calls
  `start_cluster_m14(voters, [(0, 0), (1, K)])` with the default `snap=0`. The
  log confirms both, verbatim — the pre-kill and post-kill `systemd-run` lines
  for `m12-service1` on `54.167.140.44` both end
  `--service-id 1 --work-spin 500`, with no `--snapshot-interval-bytes` (row f,
  by contrast, shows `--snapshot-interval-bytes 33554432` on every service).
- The restarted process is a fresh in-memory `SpinCountSm`, so
  `sm.last_applied()` is `None` and `attach` publishes `applied = 0`
  (`uc_service/src/attach.rs:142-155`). The apply loop's first `next_batch`
  therefore returns `Overrun` and calls `replay_into`
  (`uc_service/src/apply.rs:418-441`), which walks the journal from position 0.
- **Volume**: the arm had applied **11 858 320 commands** by the end (row c's
  `FSMS` count, `--expect-min 11854224`), essentially all of them before t0
  since the client's rate was 0 afterwards. At 64 B payload + a 16 B session
  envelope + a 32 B frame header (`uc_protocol/src/v2/frame.rs:13`), that is
  **≈ 1.3 GB of journal to re-read and re-apply** (estimate — the driver never
  printed row d's `applied` bytes; the command count is the fact).
- **The `attached_at = 21.6 s` number is a replay-completion clock, not an
  arrival clock.** `fsm_reattached`
  (`bench-infra/scripts/m14_fleet_gate.py:108-126`) requires a bumped
  incarnation **and** `lag ≤ bound`, and `uc2ctl` computes
  `lag = commit − applied` (`uc_ctl/src/main.rs:554-557`) while the slot's
  `applied` is only stored **after** `replay_into` returns
  (`uc_service/src/apply.rs:440`). So the 21.6 s is when the full replay had
  finished and left the FSM within 64 MiB of the frontier.

**This is not how a production FSM restarts.** A service configured with a
`SnapshotPolicy` installs the latest artifact and tail-replays one snapshot
interval — row f's own services, 32 MiB apart, would have bounded this to
tens of milliseconds of replay. The plan's brief chose the snapshot-less
restart; that choice, not the product, sets the ~20 s replay.

#### (ii) Client — FACT (with one measured consequence)

**Journal replay publishes nothing, so the in-flight fan-in requests could
never complete and had to time out.**

- `uc_service/src/replay.rs:44-46`, in the function's own doc: *"Leader-publish
  is **SUPPRESSED** here: these responses were already answered by the previous
  incarnation; re-emitting them onto the egress ring would be harmless
  (at-least-once) but noisy, so replay applies without publishing."* Line 60
  says the same about the reused scratch buffer. Nothing is written to the
  egress broadcast for any position walked during replay. The live path
  likewise skips already-applied positions
  (`uc_service/src/apply.rs:368-382`: apply *and* publish are both inside
  `if … Some(pos) > sm.last_applied()`).
- A fan-in submit completes **only when every declared FSM has answered**:
  `uc_client/src/engine.rs:769-786` emits `Outcome::Responses` on
  `Resolve::Won { fan_in: true }`; a piece that is not the last leaves the slot
  live via `Resolve::Partial` (lines 787-791), and only the request deadline
  retires it. The client's deadline is `request_timeout:
  Duration::from_secs(30)` (`uc_gateway/examples/m12_gate.rs:942`), and a
  `TimedOut` outcome counts as `lost` (lines 1096-1101).
- So the up-to-4 096 requests outstanding when FSM 1 died had FSM 0's half and
  never got FSM 1's: those positions were below the new incarnation's replay
  window and were re-applied **silently**. They occupied every admission slot
  until they timed out 30 s later. `--inflight 4096` is a hard count-based
  window, so with all 4 096 slots pinned the send loop could not submit a
  single new request: `try_submit_all` returned `Backpressure` for the whole
  interval.
- **The evidence matches exactly**: `client_lost = 4096`, *precisely*
  `max_inflight`, and every 2 s window after t0 reading 0. The client's arm is
  45 s and t0 lands ~12 s in, so a 30 s timeout retires the first slot at
  ≈ t0 + 30 s — after the client's own run ends. **The client's rate was
  therefore guaranteed to read 0 for the rest of the arm regardless of how fast
  FSM 1 recovered.** Row d's rate clause did not measure FSM recovery in this
  configuration; it measured the client's timeout.

This is a real client contract worth stating in its own right, independent of
the harness: **a fan-in submit is only as available as the *slowest* declared
FSM, and a fan-in client whose in-flight window is fully occupied by requests
awaiting a dead FSM makes no progress on any FSM until its request timeout
expires.** The replay-silence is correct (at-least-once semantics; a client
that needs the answer re-sends), and the pairing of the two is what pins the
window.

ladder is exhausting into the sleep path because the host is CPU
oversubscribed. `c6id.2xlarge` is 8 vCPUs, and the leader host runs the node's
four busy-spin polling agents (consensus, sender, receiver, archive) **plus**
two FSM apply threads **plus** the direct client's send and poll threads — at
least eight runnable spinners on eight vCPUs, before anything else. The ladder
is `LAG_WAIT_SPINS = 256` spins then `LAG_WAIT_YIELDS = 2048` yields
(`uc_service/src/apply.rs:526-527`, consumed by `lockstep_wait` at line
635-641) and only then the agent's 50 µs sleep. A yield budget is only as good
as the scheduler's willingness to run the peer next; when every core already
has a runnable spinner, a sibling that is descheduled cannot be woken by
yielding, the ladder runs out, the FSM sleeps 50 µs — and per M14a's own
lesson, one sleeper makes sleepers of the whole set. The measured 46.1 µs per
frame against a 50 µs sleep constant is consistent with exactly that, and the
insensitivity to `K` is what a fixed stall looks like. **"Consistent with the
symptom" is not "the cause"** (CLAUDE.md, the M12 lesson) — this is labelled a
hypothesis and nothing downstream should treat it as established.

**The test that would confirm or refute it**, either of:

- `uc_node/examples/apply_bench` under deliberate CPU oversubscription (pin
  the FSMs and a matching number of spinner threads onto fewer cores than
  runnable threads, and sweep the ratio) — the isolated-hop reproduction
  CLAUDE.md's "reproduce the collapse in the smallest isolated hop" rule asks
  for, and the cheapest of the two; or
- the same fleet arm with the **client moved to another host** (or the leader
  host sized up), which removes two spinners from the contended set. If
  lockstep's rate moves materially, contention is implicated; if it stays at
  ~21.7 k, it is not.

Until one of those runs, the honest statement is the reported number and its
shape: **lockstep costs ~60× on a `c6id.2xlarge` leader host running node,
both FSMs and the client, with a fixed ~46 µs per-frame stall that is
independent of apply cost.** The dev-box 631 k frames/s figure quoted in
`docs/reference/configuration.md` and
`docs/notes/uc2-m14-multi-service-explained.md` was measured with the FSMs
alone on the box and does **not** predict this shape; both documents now point
here.
