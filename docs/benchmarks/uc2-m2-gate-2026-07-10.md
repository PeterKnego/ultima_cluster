# uc2 M2 gate — replication stream throughput (leader → 2 followers)

**Date:** 2026-07-10

> **⚠️ THIS IS A SINGLE-HOST LOOPBACK SMOKE RUN ON A 4-vCPU SANDBOX, NOT THE
> OFFICIAL M2 GATE.**
>
> All three nodes (leader + two followers) run **in one process on one 4-core
> box**, talking over the **kernel loopback interface** — there is **no NIC and
> no wire**. The datagrams never leave the host; UDP is a `memcpy` through the
> kernel. This measures the *transport + rebuild + fsync software path* under
> artificial CPU contention, nothing about a real network.
>
> On this box the topology is **CPU-oversubscribed**: eight hot threads (the
> appender + leader tx/ctrl/archive + each follower's rx/archive) contend for
> **four cores**. The measured per-follower durable rate is therefore
> **~50–66 MB/s — BELOW the 100 MB/s bar** — and the example prints `GATE …
> FAIL`. **This is a core-count artifact, not a code defect** (see
> Interpretation): the same eight busy-spin agents that ran a single node at
> 543 MB/s in the M1 gate now split four cores eight ways, and the starved
> receivers overflow the default UDP socket buffer, triggering a self-inflicted
> retransmit storm *even at zero injected loss*.
>
> The **official M2 gate** (spec §9: **≥ 100 MB/s per follower over a real
> LAN**, durable positions keeping pace, resilient to 0.1–1 % injected loss)
> runs on **3 × c6id fleet hosts** — one node per host, each on its own 16-vCPU
> box and dedicated NIC, so there is no core-sharing and no loopback. That run
> is a follow-up with the maintainer (bench-infra has no 3-node replication
> role yet) and will be **appended to this file** when performed.
>
> **What this smoke run DOES prove** (and all of it passes): the 3-node pipeline
> runs end-to-end; both followers **converge to the full stream** (every byte
> fsync'd on all three nodes before the clock stops); NAK-driven recovery works
> under 0.5 % injected loss; and — critically — **`overruns == 0` (no wedge)**,
> validating the Task 9 pacing carry-fix. Only the *throughput number* is below
> bar, for the core-count reason above.

## What the gate measures

Spec §5 / §9: a leader appends 64 B messages into its log buffer; the sender
agent packs them into MTU-sized datagrams and MDC-fans them to two followers.
Each follower rebuilds the contiguous stream position-addressed into its own log
buffer, NAKs gaps, and its archive agent block-records + `fdatasync`es the
rebuilt bytes, advancing its durable counter. The metric is **per-follower
durable MB/s** — sustained bytes made durable on a follower per second — plus
resilience to injected loss (NAK recovery) with **zero overruns** (no gap
scrolled out of the leader's ring, i.e. no wedge).

The leader's log buffer is heap-backed (no writeback); each node's journal lives
on the "real disk" (here ext4 `/dev/sda1`; on the fleet an NVMe volume).

local NVMe) is **not** this box.

## Methodology — drain-inclusive durable rate

The headline uses **ONE wall clock around load + drain**: the clock starts before
the appender begins and stops only after **all three nodes** have made every
appended byte durable (`await_durable` on the leader and both followers). The
rate is `total_bytes / full_wall_seconds`. This is the M1 gate's accounting
lesson (see `docs/benchmarks/uc2-m1-gate-2026-07-09.md`, "Accounting
correction"): capturing the byte total *after* the drain while dividing by the
*append-window* time inflates the number by the drained-backlog fsync time that
is not in the denominator. Per-follower rebuilt rate (the per-second progress
lines) is the follower's contiguous-frontier (`append` counter) delta.

Journal dirs are on ext4 under `/home/claude` (never `/tmp`, which is RAM-backed
tmpfs on this box), and `UC2_M2_MAX_BYTES` caps the appended stream so the
bounded run fits the disk. Every journal root is `rm -rf`'d after its run; `df`
returned to the 47 GiB baseline after each.

Two pacing details, both from the Task 9 carry-fix (they are why `overruns == 0`
is reachable under loss):
- In `local` mode the appender paces `append ≤ min(live-follower durable) +
  capacity/2` — never letting the leader's ring tail scroll above where a
  follower might still NAK. (Pacing against `sent` instead, as an earlier draft
  did, put the ring tail half a buffer *above* the follower frontiers; one
  dropped datagram then left a NAK gap already scrolled out of the ring →
  `serve_nak` Overrun → permanent wedge, since replay sessions are M4.)
- The pace-wall wait `yield`s rather than busy-spins: on a core-starved host,
  spinning there would burn a core the followers need to advance durable.
  (Equivalent on a non-oversubscribed host, where the wait is rare and short.)

## Commands

Clean (no injected loss), 10 s, 64 B payloads, 256 MiB buffers, 2 GB cap:

```
UC2_M2_MAX_BYTES=2000000000 \
  cargo run -p uc_net --release --example m2_gate -- \
    local /home/claude/uc2-m2-gate 10 64 0 256
```

Loss (5 000 ppm = 0.5 %, mid-band of the gate's 0.1–1 %), 10 s, 500 MB cap:

```
UC2_M2_MAX_BYTES=500000000 \
  cargo run -p uc_net --release --example m2_gate -- \
    local /home/claude/uc2-m2-gate-loss 10 64 5000 256
```

(Both journal roots are `rm -rf`'d after their run.)

## Interpretation

- **Throughput ~53–66 MB/s per follower — below the 100 MB/s bar, and the reason
  is core count, not the transport code.** M1 ran a *single* node's appender +
  archive (two hot threads) at **543 MB/s** on the same 4-core box. M2 adds a
  second and third node in the *same process*: eight hot threads (appender,
  leader tx/ctrl/archive, and each follower's rx + archive) now split four
  cores. Each hot thread gets roughly half a core, and throughput drops
  correspondingly. On the fleet each node owns its own 16-vCPU host, so this
  contention does not exist — which is exactly why spec §9 specifies "over a real
  LAN," and why the sandbox can only smoke-test, never gate, the throughput.

- **The dup/NAK counts at *zero* injected loss are the oversubscription
  fingerprint.** The clean run shows **10 311 NAKs served and ~89 000 duplicate
  datagrams dropped with `loss 0 ppm`**. With no fault injection there is no wire
  loss — these drops happen in the *kernel*: a starved follower `rx` agent is
  descheduled long enough that the default (~212 KiB) UDP socket receive buffer
  overflows, the kernel drops datagrams, the follower NAKs the gap, and the
  retransmit (plus the delayed original) arrives as a duplicate. This retransmit
  storm is pure wasted CPU that further starves the pipeline — a self-inflicted
  congestion spiral that only exists because eight busy-spin agents share four
  cores with a small socket buffer. On the fleet (dedicated cores, and the large
  `SO_RCVBUF` a real deployment sets) it disappears.

- **The M2 correctness invariants all hold — this is what the smoke run
  validates:**
  - **`overruns == 0` on both runs** — no NAK gap ever scrolled out of the
    leader's ring; the leader never had to abandon a follower to a (not-yet-
    built) replay session. This is the direct validation of the Task 9 pacing
    carry-fix; under the old `sent`-pacing the 0.5 % loss run would have wedged
    (`serve_nak` Overrun) and `await_durable` would have hung to its 300 s
    deadline.
  - **Both followers converge to the full stream** — the run only reaches the
    final report after `await_durable` confirms every appended byte is durable on
    the leader *and* f1 *and* f2 (865 MB clean, 500 MB under loss). Under 0.5 %
    loss the tail is drained entirely by NAK recovery: **8 135 NAKs served,
    ~8 100 sent by the followers**, zero `dropped_stale_term`, zero
    `dropped_malformed`.
  - **`flow_stalls == 0`** — the quorum-order-statistic flow control never
    clamped the sender below a full frame; the throughput ceiling here is CPU,
    not the flow window.

- **Drain-inclusive accounting, honestly applied.** The clean headline divides
  865 MB by the full 13.08 s (load + drain), not by the 10 s append window; the
  per-second lines continue past t=10 s (t=11..13 s) because after the appender
  stops the followers are still draining their backlog to durable — those
  seconds are *in* the denominator, as they must be. The loss run's cap binds at
  500 MB in 9.39 s.

## Fleet (3 × c6id, real LAN) result — 2026-07-11: **PASS**

**The spec §9 M2 bar is passed with 2.3–3.2× margin, including under injected
loss.** 3 × c6id.2xlarge, us-east-1, cluster placement group, private-IP LAN,
one `m2_gate` role per host, journals on local NVMe, fsync on, 64 B payloads,
256 MiB buffers, 15 s runs (source = merged main 849d3e9).

**Clean run:** leader appended+durable 4,510,178,560 B (46.98 M msgs) in
15.19 s; both followers rebuilt at ~272–311 MB/s sustained and drained
`durable_lag` to 0. The LAN itself dropped exactly one datagram across the
run — recovered via NAK (`naks_served 1`), a free real-world validation of
the loss path. `overruns 0`.
