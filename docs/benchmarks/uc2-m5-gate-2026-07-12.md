## What the gate measures

Spec §9's milestone table (`docs/superpowers/specs/2026-07-09-uc-v2-aeron-shaped-smr-design.md`),
verbatim:

| # | deliverable | gate |
|---|---|---|
| M5 | SDK/apply/protocol v2 e2e | full lincheck + crashtest green; **client→apply→response ≥ 400k @ p50 ≤ 1ms (headline bar)** |

and the project-wide success bar (§2): "**≥400 k msg/s, p50 ≤1 ms, fsync on,
linearizable, 3×c6id fleet** (stretch: 800 k parity); correctness gates
non-negotiable."

Unlike M3 (which measured the **commit pipeline alone** — leader append →
quorum-fsync'd commit, no SDK in the loop), M5 measures the **full production
round trip**: a client process writes a submit record onto the node's
`ingress.ring` (shared memory, MPSC), the node's consensus agent appends +
replicates + commits it (the M3/M4 pipeline underneath, unchanged), the
service's apply agent polls the committed log directly out of the mapped
buffer, applies it to the user state machine, and publishes the response onto
`egress_service.broadcast`; the client's matcher thread picks its own answer
out of that shared broadcast and the clock stops there. Every layer of the M5
SDK (Tasks 1–14b: cnc v2, IPC rings, apply loop, egress, client attach) is
inside the measured path — this is the number that determines whether the
whole v2 stack, not just its consensus core, holds the bar.

**Correctness prerequisite (already met, not re-measured here):** the full
in-process WGL lincheck capstone (`uc2_node/tests/lin_v2.rs`,
`linearizable_under_failover_v2`) and the multi-process SIGKILL crashtest
(`examples/uc2-crashtest`, `hard-crash-tests` feature) both pass — see the
Task 13/14 commits (`a8b1b5c`, `1172c65`) and the workspace suite run below.
M5's gate is these correctness proofs **AND** the throughput/latency bar; this
doc is the second half.

## The measuring client's mechanics

The `client` role deliberately bypasses `uc2_client`'s per-request
channel/mutex machinery (plan decision #6 — a benchmark driver has no business
paying a `mpsc::sync_channel` + registration-table lock per op). It opens the
exact same real files a production client would (`cnc2.dat`, `ingress.ring`,
`egress_service.broadcast`, `egress_node.broadcast`) and allocates its
`client_id` the same way (`next_client_id.fetch_add`, generation-random per
Task 14b), but correlates requests to responses through a **pipelined
correlation table** instead of a channel:

- `send_ns: Box<[AtomicU64]>`, `SLOTS = 1<<20`, indexed `local_seq &
  (SLOTS-1)` — the send timestamp (ns since the client's `t0`), stamped by the
  sender thread immediately before the `ingress.ring` write.
- `owner: Box<[AtomicU64]>`, same shape — holds `local_seq + 1` while a send
  is outstanding, `0` once resolved. A dedicated matcher thread claims
  resolution with a single `compare_exchange`, so exactly one delivery per
  `local_seq` counts (see "Duplicate-response tolerance" below).
- An inflight window `W` (`--inflight`, default 4096) caps `sends - resolved`;
  the sender yields+retries while the window is full. Admission itself is the
  node's own ring-door (`RingError::Full` on `try_write` → yield+retry) —
  identical backpressure contract to the real `uc2_client`.
- A serving gate: the sender pauses (1 ms sleeps, no sends) while the
  attached node's cnc `CAN_SERVE` flag is clear — the measuring-client mirror
  of a real client's NOT_LEADER backoff (see the smoke section for why this
  matters).
- The matcher computes `now - send_ns[slot]` into an `hdrhistogram::Histogram`
  (the same crate/pattern as `examples/counter_loop`'s bench driver) for every
  genuine first-arrival `MSG_V2_RESPONSE`.

Reported: **responses/s** (drain-inclusive, floored at the send window's end —
see below), **p50/p90/p99/max**, **sends**, **responses**,
**in-flight-at-end**. **PASS iff `responses/s ≥ 400_000 && p50 ≤ 1.0 ms &&
in-flight-at-end == 0`** (the completion criterion is strict, no epsilon: a
healthy run gets a 5 s drain grace to resolve a tail of at most `W`
outstanding requests — milliseconds of work at even 1 % of the target rate —
so any residue means responses stopped arriving or were lost, and the numbers
describe a run that did not finish); else `RESULT: FAIL (honest)` + `exit(1)`.

An earlier 10 s run of the same measurement mechanics (before the bar line
gained the in-flight criterion) caught a mid-run leadership blip live (the
core-starved election timeout fired spuriously — an expected sandbox
artifact, not a v2 correctness bug: M4's failover machinery is exactly
what's supposed to fire here): 2,304 sends were redirected
`MSG_V2_NOT_LEADER` during the blip and every one of them **resolved
cleanly** — no hang, no stuck inflight slot, `in-flight at end: 0` — after
which the client's serving gate held sends until n1 served again and the
measurement resumed (final: 2,953,893 responses, 293,076/s @ p50 6.500 ms,
FAIL honest). Two mechanisms are visible in that run:

- **`NOT_LEADER` resolves the inflight slot** (not just `MSG_V2_RESPONSE`),
  so the sender never wedges against a request that will never get a real
  answer.
- **The serving gate pauses sends while the attached node is not serving.**
  Earlier sandbox iterations of this binary lacked the gate, and a mid-run
  leadership flip degenerated into a redirect feedback flood: each
  `NOT_LEADER` freed its window slot instantly, reopening the inflight
  window, so the sender free-ran at ring speed — one gate-less run produced
  **31 M redirect "sends" in 10 s**, junk load that starved the very
  consensus agents trying to re-elect and measured nothing. The gate (the
  measuring-client mirror of a real client's NOT_LEADER backoff) turns a
  leadership stall into what it honestly is: missing throughput for its
  duration, visible in the drain-inclusive rate.

### Standalone-process sanity check (node/service/client as separate OS processes)

The `all` role runs everything in one process for convenience; the fleet uses
the standalone `node`/`service`/`client` binaries as separate processes. A
quick single-node (no real quorum — 1-of-1) manual check confirms that path
independently:

```
cargo run --release --example m5_gate -- node    --id 0 --bind 127.0.0.1:PORT \
    --members 0@127.0.0.1:PORT --instance-dir DIR --admission-kib 256   &
cargo run --release --example m5_gate -- service --instance-dir DIR         &
cargo run --release --example m5_gate -- client  --instance-dir DIR --secs 3 \
    --payload 64 --inflight 512
```

**This PASS is not a gate result and must not be read as one.** It is a

## Honest notes

- **Drain-inclusive clock, floored at the send window's end.** `responses/s`
  divides the response count by the elapsed time from the client's `t0`
  (immediately before its first send) to **`max(last resolved response,
  send-window end)`** — not the send loop's own wall time. Both halves of the
  `max` guard an inflation direction:
  - *last-response half:* a send loop that finishes at `--secs` still has
    outstanding requests in flight; those keep resolving (and keep advancing
    the denominator) during the post-loop `DRAIN_GRACE` window. This is the
    M1/M3 accounting lesson — dividing by a window that excludes the drain
    inflates the number.
  - *send-window-end half:* taking the last response alone would let a run
    whose responses **stop arriving mid-window** (service permanently behind
    while the node keeps `CAN_SERVE` — zero redirects, serving gate open,
    last-response timestamp frozen early) silently excise its dead tail from
    the denominator and report the early burst's rate as the run's rate. The
    floor makes a dead tail depress responses/s instead of vanishing — and
    the `in-flight-at-end == 0` PASS criterion (above) fails such a run
    outright regardless.
- **Duplicate-response tolerance (Task 14b).** A service that restarts
  mid-run reconstructs by replaying the committed log from the top and
  legitimately **re-publishes** historical responses under their *original*
  `(client_id, local_seq)` — the at-least-once contract a client survives a
  service-only crash. The `owner[]` slot array's `compare_exchange` makes
  resolution exactly-once: the FIRST delivery for a given `local_seq` wins the
  claim and is the one timed/counted; any later delivery for the same
  `local_seq` (a genuine duplicate, or a stale delivery for a slot the sender
  has since reused for a newer send) finds a non-matching `owner` value and is
  dropped into the `dup responses dropped` counter — never double-timed, never
  double-counted toward throughput. This did not fire in the smoke runs above
  (no faults were injected — M5's gate is a stability measurement, not a
  failover one; that is M4's territory) but is exercised directly by the L3
  lincheck capstone's service-crash fault, which shares this same
  `(client_id, local_seq)` + re-publish contract.
- **What this client measures vs. what M3 measured.** M3's `m3_gate` measured
  the **commit pipeline only**: leader append → quorum-fsync'd commit, no SDK,
  no apply, no IPC to a separate service process, latency sampled every 1024th
  append. `m5_gate`'s client measures the **entire user-visible round trip**:
  shmem ring write → node consensus/replication/commit (M3's pipeline,
  unchanged) → service apply (a separate process/thread reading the committed
  log) → egress broadcast → client matcher — i.e. it is a strict superset of
  what M3 measured, with the SDK/IPC/apply hops added on top. A slower number
  here than M3's committed/s is expected and correct; the SDK hops are real
  added latency/throughput cost, and the whole point of M5 is proving they
  don't blow the bar.
- **Sandbox core-starvation, restated.** 4 vCPU hosting 3 nodes × 4 agents +
  3 services + 1 client + 1 matcher is roughly 18 threads meaningfully
  competing for 4 cores. The sandbox p50s here (multi-millisecond) are
  consistent with scheduling latency, not an architectural signal — same
  conclusion the M3/M4 sandbox docs reached, now reconfirmed on the layer
  above the commit pipeline.
- **Payload accounting.** `--payload N` is the length of an OPAQUE raw byte
  buffer; the wire command is `bincode(Vec<u8>)` (that buffer), a few bytes
  larger than `N` for the length prefix, and `CountSm::apply` never inspects
  the content — it only counts arrivals. This mirrors the spirit of
  `uc2_service`'s "`AppCommand` bytes flow ring→frame→apply with exactly one
  deliberate copy" contract; the gate's SM is deliberately the cheapest
  possible `apply` so the measurement isolates the SDK/IPC path rather than
  any business logic.

## Fleet run protocol (not yet performed)

Per the M3 admission-window discipline (`docs/benchmarks/uc2-m3-gate-2026-07-10.md`):
**read the bar at the BEST point of a sweep, never at one default** — a single
default-window run that misses the bar is not evidence the architecture
missed it.

- **Topology:** 3 × c6id.2xlarge, single AZ, cluster placement group (M3's
  proven fleet setup). One node + one service process **per host** — all
  three hosts run both roles; this is the real deployment shape (client is
  same-host shmem only, node/service co-located).
- **Binding:** every node binds its **concrete private-NIC IP** (never
  `0.0.0.0` / loopback) — the M3 fleet doc's binding gotcha applies
  unchanged (a wildcard-bound follower's reports get dropped at the
  membership guard and commit silently stalls).
- **Instance dirs:** NVMe under `/opt/bench` (fleet convention; ansible
  provisions this as the fast local volume) — never the AMI's root EBS.
- **Process lifecycle:** every host runs its `node` and `service` processes
  under `systemd-run` (fleet-ops convention — plain `ssh ... &` hangs the
  driving session; `systemd-run` detaches cleanly and gives a real unit to
  stop/inspect). Host A additionally runs the `client` role locally (against
  its own co-located node — cross-host shmem does not exist, so the client's
  host must be wherever the leader is; if host A's node is not the leader at
  client-start, `await_serving` in the client binary blocks up to 30 s for it
  to become one — arrange the run so host A's node wins the election, or wait
  out the election before starting the client).
- **Admission sweep:** `--admission-kib` = **64 / 128 / 256** on every node
  (must match across all three — the admission window is a leader-local
  pacing knob, but keeping it uniform avoids conflating a follower-side
  config difference with a real result). Evaluate the ≥400k/p50≤1ms bar at
  the best point of the sweep, exactly like M3.
- **Duration:** ≥15 s per sweep point (M3 precedent) so the drain-inclusive
  clock's tail is a small fraction of the total.
- **Mid-run leadership loss invalidates the point.** If leadership moves
  during a run (visible as a nonzero `not_leader redirects` count and a
  send-gate pause), the throughput number mixes a dead window into the
  denominator — re-run that sweep point rather than reading a depressed
  number as a result. On the placement-group LAN with per-host dedicated
  cores this should not happen (M4 measured election stability under load);
  it is routine on the core-starved sandbox.
- **A large `in-flight at end` invalidates the point too — the service-stall
  class.** A run can go dead WITHOUT any redirect: the node keeps
  `CAN_SERVE` (so the serving gate stays open and `not_leader` stays 0)
  while the service stops resolving — service process wedged/killed, apply
  loop stuck in replay, or the client's own broadcast reader lapped
  (`broadcast overwritten` > 0). The binary already refuses to print PASS in
  this state (`in-flight at end == 0` is part of the bar) and the
  send-window floor keeps the dead tail in the denominator, but the
  depressed responses/s of such a run is a *diagnostic*, not a sweep-point
  result: diagnose (service logs, `broadcast overwritten`, cnc
  `service_heartbeat_ns`) and re-run the point.
- **What "GO" looks like:** at least one admission-window point in the sweep
  clears `responses/s ≥ 400_000 AND p50 ≤ 1.0 ms AND in-flight at end == 0`,
  with `RESULT: PASS` printed by the `client` role itself (not inferred —
  the binary's own PASS bar is spec §9's bar plus the run-completed
  criterion).
