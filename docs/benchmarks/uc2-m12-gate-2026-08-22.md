## What M12a is

M12a is the first of four M12 sub-milestones (M12a gateway kit → M12b admin
authn/audit → M12c packaging/publishing → M12d posture + review), tagged
together as `v2.6.0` once all four land. M12a ships: the **two-tier
state-machine contract** (`RawStateMachine` bytes-in/bytes-out as the core
trait, today's typed `StateMachine` kept as a blanket adapter —
`docs/reference/state-machine-contract.md`), the **`Sessioned<S>`** exactly-
once session-envelope wrapper, and **`uc2_gateway`/`uc2_remote`** — a TCP
edge (`Edge`) that terminates the framed remote protocol on a node's host and
relays it over the existing shmem `Engine`, plus a pipelined, credit-gated,
redirect-following Rust client (`RemoteClient`). None of this touches
consensus, the wire protocol between nodes, or the cnc page — a cluster with
no gateway running is unchanged.

## What M12b is

M12b (Tasks 1–7 on `uc2/m12b-admin-auth`, HEAD `cca681d`) ships **admin
authentication and audit**: an HMAC-SHA256-signed admin request (a new
64-byte cnc line, `CNC_OFF_ADMIN_AUTH = 3904`), an append-only audit log
(`<instance_dir>/audit.jsonl`, one `fsync`ed JSON line per admin answer,
written before the answer is published), and two explicit-choice config
sections (`[crypto].enabled`, `[admin]`) that turn "off by default" into
"stated by default" — an absent section is now a named startup refusal
rather than silently cleartext/unauthenticated. No wire protocol bump (the
cnc page grows within its existing reserved band; node-to-node datagrams are
unchanged). Row 4 below is M12b's row; every other row is
unaffected by this sub-milestone.

## What M12c is

M12c (Tasks 1–5 on `uc2/m12c-packaging`) ships **packaging, publishing and
hygiene** — the parts of "a stranger can adopt this" that are not code the
cluster runs:

- **Version identity.** Lockstep `2.6.0` across `[workspace.package]`, all
  twelve publishable crates, the git tag, the tarball names and the image
  tag; publish metadata (description/keywords/categories/license/repository)
  on every one; `uc2_sim`, `uc-lincheck` and the example crates explicitly
  `publish = false`. The promise that version number makes is written down in
  `docs/reference/semver-policy.md`.
- **Supply chain.** `deny.toml` + two `cargo-deny` passes in CI; dead
  `quinn`/`rustls`/`tokio`/`futures` deps removed; `snow`'s `std` feature
  dropped so exactly one AES-GCM implementation is in the graph.
- **A stated MSRV.** `rust-version = "1.89"`, a pinned `rust-toolchain.toml`
  (1.96.0), and an `msrv` CI job that runs clippy on the real floor.
- **Release artifacts.** `.github/workflows/release.yml` — native x86_64 and
  aarch64 builds, tarballs + `SHA256SUMS` + a CycloneDX SBOM, cosign keyless
  signing, a GitHub Release, and a signed multi-arch `ghcr.io` image — all
  gated on `release-smoke`, which runs the artifact's own quickstart in a
  bare `ubuntu:24.04` and then the same binaries as a compose stack.
- **A quickstart that needs no toolchain.** `packaging/quickstart-local.sh`
  (three nodes, three services, three gateways, a real election, two
  committed writes and a linearizable read driven from outside by the new
  `counter-remote` example binary), plus `packaging/Dockerfile` and
  `packaging/compose.yml`.
- **Docs.** An artifacts-first `docs/QUICKSTART.md`, install-from-release in
  `run-a-cluster.md` and the runbook, `docs/how-to/cut-a-release.md`, and
  `docs/reference/semver-policy.md`.

M12c changes nothing a running cluster does: no consensus change, no wire
protocol change, no cnc layout change. One product-visible fix rode along
with it (Task 3b): `uc2_remote`'s `request_timeout` is now enforced *while*
the reader is reconnecting, not only once connected — see
`docs/reference/remote-protocol.md` for the documented bound. Rows 5, 6, 7
below are M12c's rows, plus rows 11–13 added for spec §6's hygiene items.

```

p50 ratio (gw/direct) : 9.675  (83.296 ms / 8.610 ms)
p99 ratio (gw/direct) : 22.178  (513.802 ms / 23.167 ms)

--envelope off
responses/s ratio     : 0.074  (28387 / 385369)
p50 ratio (gw/direct) : 12.642  (109.052 ms / 8.626 ms)
p99 ratio (gw/direct) : 8.645  (198.574 ms / 22.970 ms)
```

Direct-arm absolute numbers land close to the M5 headline bar's raw figures
(~385k–398k responses/s @ p50 ~8.6 ms on this box) despite this box never
having cleared that bar in its own dev-box smoke history.

**The two arms run ONE AFTER THE OTHER, never concurrently** (`main()` runs
`run_direct_arm()` to completion — including stopping all three of its
nodes and services — before `run_gateway_arm()` starts; `uc2_gateway/examples/m12_gate.rs`).
So the low ratio is not "two clusters splitting one box's cores"; it is two
SEPARATE oversubscription stories, one per arm, on the same shared 4-vCPU
box:

1. **Each arm, on its own, already oversubscribes this box.** The direct
   arm alone is 3 busy-spinning nodes (consensus/sender/receiver/archive
   agents each) + 3 services + the measuring client contending for 4 vCPUs —
   the same non-representative crowding the M5/M11 smoke docs already call
   out, before a gateway is in the picture at all. The gateway arm repeats
   that same 3-node + 3-service crowding and ADDS three more things
   competing for the same 4 cores: 3 edges (each an acceptor thread + a
   driver thread), the `RemoteClient`'s reader thread, and this harness's
   own 8-thread waiter pool. That is strictly more concurrent work on the
   same core count, which alone would depress the gateway arm's numbers
   relative to the direct arm even if the gateway added zero real cost.
2. **On top of the oversubscription, the gap is also architecturally real —
   see fact (d) below.** A single edge's driver thread writes every response
   for every connection sequentially (`edge.rs`'s "Head-of-line blocking"
   section), and `RemoteClient` funnels every submit/response through one
   `Mutex<State>` (`client.rs`'s "One lock, one order"). Both are genuine,
   documented single-writer constraints that will still cost something on a
   fleet host with a core to spare; the fleet run is what states how much of
   the local ratio survives once the oversubscription confound above is
   removed.
3. This harness's own waiter pool (8 threads, each with its own histogram —
   no shared lock on the recording hot path, fixed during this task after an
   initial run showed a `Mutex<Histogram>` contention artifact) is not
   itself the bottleneck: the credit-gated pipeline (per-connection window
   4096, matching `--inflight`) queues far deeper than 8, and the measured
   p50/p99 track queueing depth against throughput, not per-request network
   RTT.

## Facts the gate must state (spec §4.6 / design notes, binding across every
future fleet re-run of row 2)

a. **With the raw contract, every replica — followers and the replay path,
   not just the leader — runs the typed adapter's response encode.** Only
   `publish` (making the response visible to a client) is leader-gated; the
   apply-side decode/encode cost in `docs/notes/2026-08-22-codec-budget-spike.md`
   is paid on every node, every commit.
b. **`credits.rs` (`uc2_gateway/tests/credits.rs`) proves the per-connection
   credit ceiling over the wire.** The AIMD descent (the credit squeeze on
   `Backpressure`) is covered by `conn.rs`'s unit tests only — there is no
   integration test today that drives a real `Backpressure` condition over
   the wire and observes the halve-then-climb-back behavior end to end.
c. **The remote lincheck capstone (row 1) is `submit` → `wait` at
   concurrency 4** (one request in flight per worker, by construction — an
   op must be a single interval to be a linearizability history entry at
   all). The SDK's *pipelining* (many outstanding requests per connection)
   is exercised by `failover.rs`'s 200-write scripted run and by this
   document's own `m12_gate` throughput harness, not by the capstone.
d. **The single driver thread per edge serializes outbound writes.** A
   stalled client's write (up to `WRITE_TIMEOUT` = 1 s) can delay every other
   client's responses on that edge — `edge.rs`'s "Head-of-line blocking"
   section documents the mechanism and its consequence (a stalled peer can
   make another client see `UNKNOWN`, resolved by re-send under the session
   envelope). Any fleet cost number for row 2 includes this cost; it is not
   an artifact to be tuned away before reporting.
e. **Commands are MTU-bounded to ~1.3 KB.** `uc_protocol::v2::datagram::MTU_DEFAULT`
   = 1408 B is not operator-configurable; a raw command payload above that
   cannot fit one datagram (`Sender::new`'s hard assert) regardless of
   transport.
f. **`SessionConfig` (`window`, `max_clients`, `max_bytes`) is part of the
   replicated contract**, exactly like `apply` itself: every replica running
   `Sessioned<S>` must run with identical `SessionConfig` values, and
   `install_snapshot` refuses a snapshot whose embedded config disagrees with
   the live node's rather than silently retuning it (`session.rs`'s module
   doc).
g. **The two arms' completion-timestamp mechanisms are not identical, a
   small asymmetry inherited from `m5_gate`.** The direct arm's matcher
   thread polls in a loop with a 20 µs idle-sleep floor between empty polls
   (`run_client_measurement`'s poll loop), so a response's recorded
   timestamp can lag its real arrival by up to ~20 µs; the gateway arm's
   waiter threads instead block on `Ticket::wait_timeout`, so a response is
   timestamped as soon as the OS wakes the blocked thread. Neither biases
   the ratio in the gateway's favor, but it means the two arms' latency
   numbers are not measuring completion detection the same way.

## M12b facts (binding on row 4, and on any future reader of this doc)

a. **One `fsync` per admin op, on the consensus thread, not the hot path.**
   `AuditLog::record` (`uc2_node/src/audit.rs`) does one `write_all` plus one
   `sync_data` per admin decision, and every answer site (the local cnc
   response line, the kind-17 forwarded-config reply) calls it before
   publishing. **One carve-out, added by the final review (I4):** a
   byte-identical re-send of an already-answered, already-recorded proposal
   — same nonce, served from the leader's dedup cache — is counted
   (`config_proposal_dedup_resend`), not re-recorded, because it repeats an
   answer this file already holds rather than being a new admin event. That
   is what bounds the fsync half of fact (c) below; every request that
   produces a fresh decision is still recorded before that decision is
   published. Admin operations are operator-rate — tens a year on a busy
   cluster — so this cost (a few ms on ordinary storage) is paid at most a
   few times a year, never inside `apply`/replication/archive's per-cycle
   loop. If the write or the `fsync` fails, the request is refused
   (`REASON_AUDIT_FAILED = 24`) rather than answered unrecorded — see
   `uc2_node/src/node.rs`'s `audit_admin`.
b. **No `(seq, nonce)` replay ring, a deliberate deviation from spec §5.2's
   sketch.** The HMAC tag covers `seq`; the consensus agent only ever acts
   on `seq > last_admin_seq`, so a captured request cannot be re-presented
   at its original `seq` (never even read again) and re-presenting it at a
   higher `seq` invalidates the tag. Across a node restart `last_admin_seq`
   resets to 0, but the tag also covers `instance_id`, which changes on
   every restart. A ring would therefore never refuse anything these two
   checks do not already refuse; `expiry_ns` is what bounds the window for a
   live, correctly-sequenced request that is delayed and only then applied.

   **The `instance_id`/`app_id` the tag is bound to come from the node's own
   boot-time state, not from the cnc page** (`Consensus::admin_instance_id`
   / `admin_app_id`, set in `Node::start_with` from the same values it
   writes into `CncMeta`). The final review found this the other way round —
   `verify_admin` read `self.cnc.meta()` per request — which made the
   restart half of the argument above false: the cnc page is a file in the
   instance directory, `read_cnc_header` validates only its magic, so an
   actor with directory write access and NO admin key could capture a signed
   `(auth, req)` pair, await or induce a restart (resetting
   `last_admin_seq` to 0), `pwrite` the captured `instance_id` back into
   `CNC_OFF_INSTANCE_LO/HI`, re-present the captured lines, and have the
   change applied a second time. Fixed, and pinned by
   `uc2_node/tests/admin_auth.rs::a_capture_replayed_after_a_restart_is_refused`,
   which performs exactly that forgery and asserts reason 21 with the config
   version unmoved. (Anti-vacuity: with the binding reverted to
   `cnc.meta()`, that test's replay verifies and reaches `propose_config`,
   coming back as reason 5 `AlreadyPresent` rather than 21.)
   See `verify_admin`'s doc comment (`uc2_node/src/node.rs`) and
   `uc2_node/tests/admin_auth.rs::a_replayed_request_cannot_be_re_presented`,
   and the spec's own "As built" amendment (§5.2).
c. **The kind-16 residual: admin auth is cluster-wide only with wire crypto
   on.** A follower forwards an authenticated request to the leader as a
   `ConfigProposal` datagram (wire kind 16) over the node-to-node UDP
   socket, not the admin band. `on_config_proposal`'s membership guard drops
   a datagram whose source address resolves to no current member before any
   work runs, but with `[crypto].enabled = false` a network-path adversary
   who can send UDP claiming a member's address can still inject a
   proposal — `[admin] auth = "hmac"` authenticates cluster-wide only paired
   with `[crypto].enabled = true`. Stated in
   `docs/reference/configuration.md#admin-authentication`,
   `docs/how-to/change-cluster-membership.md`,
   `docs/how-to/encrypt-node-traffic.md`, and `README.md`'s scope section.

   **The audit-`fsync` half of that residual, bounded (final review, I4).**
   Every kind-16 datagram past the membership guard used to write an audit
   record — including the nonce-dedup re-answer path, so one captured
   datagram re-sent in a loop drove one `fsync` per packet on the consensus
   thread. `on_config_proposal` now re-sends the cached reply WITHOUT a
   second record (the original answer was recorded; a byte-identical
   re-answer of the same nonce is not a new admin event) and counts it as
   `config_proposal_dedup_resend`; unit test
   `uc2_node/src/node.rs::a_dedup_re_send_is_counted_not_re_audited`. The
   remaining residual is stated rather than closed: a flood of FRESH nonces
   from a member — or, with `[crypto].enabled = false`, from anything that
   can spoof a member's source address — still costs one `fsync` each. It is
   bounded by the membership guard, and with `[crypto].enabled = true` by
   peer authentication, which is the same pairing the paragraph above
   states.
d. **`AdminPolicy` is not a `NodeConfig` field.** It lives on
   `StartOpts::admin`, alongside the pre-bound socket — both are live
   process resources, not values a `Clone`-able TOML-mirroring config struct
   should carry. `Node::start`/`Node::start_with_socket` (library callers,
   every in-process test and gate) get `StartOpts::default()` =
   `AdminPolicy::Filesystem`, byte-for-byte the pre-M12b posture; only the
   `uc2-node` daemon (`uc2_node/src/bin/uc2-node.rs`) builds `AdminPolicy`
   from `[admin]` and calls `Node::start_with`.
e. **`admin_auth.rs`/`daemon_refusals.rs` run in the fast per-PR job.**
   `.github/workflows/ci.yml`'s "Tests (uc2_node fast integration)" step
   lists `--test admin_auth --test daemon_refusals` alongside
   `smoke`/`failover`/`learner`/`purge_safety`/`query_barrier`, so the admin
   authn+audit net is a per-PR gate, not a nightly-only one. (It was
   nightly-only when Tasks 1–3 landed — the `--test` list simply was not
   extended — and the final review fixed that.) The two suites are 10 + 3
   tests, ~4.6 s total on this box, well inside the fast job's budget.
   `uc2ctl/tests/admin_auth_bin.rs` is covered per-PR too, via `cargo test
   --workspace --exclude uc2_node` (`ci.yml`'s second test step, which does
   not filter by test file the way the `uc2_node` step does).

## M12c facts: what is validated locally, and what is CI-only

The honest split, because rows 5 and 6 turn on it. Everything in the first
list was actually run on this dev box on 2026-08-23; everything in the second
is written and reviewed but has never executed anywhere, and the first real
run of it is the `v2.6.0-rc.1` tag the user pushes.

**Validated locally (dev box, 2026-08-23):**

a. `packaging/quickstart-local.sh` end to end against a release-profile bin
   directory — three `uc2-node`s, an election won by node 0 in term 1, three
   `counter-service`s, three `uc2-gateway`s, then `reset` → `value=0`,
   `add 5` → `value=5`, `add 5` → `value=10`, `get --linearizable` →
   `value=10`, `PASS`, exit 0. The transcript in `docs/QUICKSTART.md` §2 is
   that run, verbatim.
b. The **tarball assembly and layout** — the exact
   `dist/uc2-<ver>-<target>/{bin,packaging,LICENSE,README-release.md}` tree
   `release.yml` builds — extracted and driven through
   `quickstart-local.sh --bin-dir <extracted>/bin`, plus `sha256sum -c` on
   the tarball (Task 4).
c. The compose `init` service's **rendered `node.toml`/`gateway.toml` fed to
   the real loaders** (`uc2-node`/`uc2-gateway` reach a runtime bind/attach
   error, i.e. every config check passed) — Task 4.
d. `publish-check`'s first two steps, both green:
   `scripts/check_publish_metadata.sh` (`ok: publish metadata (keywords,
   categories) within crates.io limits`) and the batched
   `cargo package --no-verify` over all 12 publishable crates (exit 0; each
   crate reports its packaged file count).
e. `cargo deny --all-features check` (Task 1 fix round) and the MSRV
   toolchain probe — `cargo +1.89.0 check --workspace --all-targets
   --locked`, `cargo +1.89.0 test -p uc2_crypto -p uc_protocol --locked`
   (132 + 71 passed), and `cargo +1.89.0 clippy --workspace --all-targets
   --locked -- -D warnings` — all green after the two targeted `allow`s.
f. `cargo doc --workspace --no-deps --lib` (the shape `docs.yml` builds) and
   `cargo clippy --workspace --all-targets -- -D warnings` after the Task 5
   documentation sweep.

**CI-only, or unproven until the first `-rc` tag:**

g. **Docker, buildx, docker compose and ghcr are unavailable on this box.**
   So the `release-smoke` bare-container run, the `packaging/Dockerfile`
   image build, the three-node compose stack and the ghcr push are validated
   in CI only. `scripts/release_smoke.sh` itself has never been executed
   here; only `bash -n` and `shellcheck` have.
h. **Keyless cosign signing is not provable here and deliberately was not
   attempted.** It needs a GitHub OIDC identity this box does not have; a
   local `cosign sign-blob` would either fail or, worse, produce a signature
   under some *other* identity, which is not what row 6 claims. A
   `workflow_dispatch` dry run does not reach it either — the `release` and
   `image` jobs are guarded on `startsWith(github.ref, 'refs/tags/v') &&
   !inputs.dry_run`. Only a real tag does.
i. **aarch64 binaries are built but never executed.** `release-smoke` runs
   the x86_64 tarball only, so row 5 is claimed for x86_64 and unclaimed for
   aarch64 until somebody runs the arm tarball on arm hardware —
   `docs/how-to/cut-a-release.md` §4 asks for exactly that at the rc tag.
j. **The 12-crate crates.io publish has never run.** Row 7 proves packaging
   for all 12 and `--dry-run` for the 4 leaves; the real publish is the
   manual ordered sequence in `cut-a-release.md` §6, first exercised at the
   tag.
k. **`cargo fmt` is deferred**, with the condition to re-run it stated in
   row 13.
