# uc2 M8 gate — opt-in authenticated/encrypted node-to-node transport

**Date:** 2026-07-29
**Branch:** `uc2/m8-wire-crypto`
**Status at the time this section was written:** **RULE PRE-COMMITTED, NOTHING
MEASURED YET.** This file is committed *before* either arm runs. Everything

## Why the rule comes first

This project has an explicit precedent for it. The read-profile arc
(`docs/benchmarks/uc2-read-profile-2026-07-26.md`) committed its decide rule
and its kill-criteria to the repository before a single fleet second was
bought, and that is the reason its conclusion — "the read barrier costs ~58%,
and after Rung A it costs ~0%" — is worth anything. A bar chosen after seeing
the number is not a bar, it is a description.

So: **the bar below is fixed as of this commit.** If the encrypted arm misses
it, this document records an honest FAIL and the real number, the investigation
that follows goes looking for a cause, and the bar does not move.

## Pre-committed decide rule

> **PASS iff encrypted throughput ≥ 90% of the cleartext control**, i.e. the
> crypto arm's `responses/s` is no worse than a **10% regression** against the
> cleartext arm measured immediately before it.

Method constraints, all fixed in advance:

| constraint | value |
|---|---|
| arms | cleartext **control first**, then encrypted |
| box | the same box, back to back, no reboot or rebuild between arms |
| seed | identical (`m5_gate`'s `seed_for(id)`, unchanged in both arms) |
| duration | identical `--secs` |
| payload / inflight | identical |
| primary metric | `responses/s` as printed by the harness |
| secondary (reported, **not** part of the bar) | p50/p90/p99/max, in-flight-at-end |
| repeats | **3 per arm, interleaved** `control, crypto, control, crypto, control, crypto` |
| statistic adjudicated | the **median** of each arm's 3 `responses/s` values |

**The repeat protocol is pinned here, before any arm has run** (added in the
same pre-run commit series as the bar itself, `17baf9d`…). This box is shared
and its ambient load varies, so a single pair could be decided by a background
process rather than by cryptography. Interleaving the arms spreads any drift
across both, and the median of three discards a single outlier without letting
anyone pick the flattering pair afterwards. `uptime` is recorded next to every
run so a reader can judge the load for themselves. **All six runs are printed
verbatim regardless of what they say.**

**Secondary metrics are reported but do not gate.** The bar is throughput
only. Latency is recorded so a reader can see what happened, and a latency
blow-up with intact throughput would be called out in prose — but it does not
retroactively become part of a bar that was written down as throughput.

### Reference point (not the bar)

The M5 fleet gate, the project's headline number
(`docs/benchmarks/uc2-m5-gate-2026-07-12.md`):

> **1,639,187 responses/s @ p50 0.600 ms**, 3 × c6id.2xlarge, quorum
> replication, fdatasync per block.

That is the number wire crypto must not meaningfully erode **on the fleet**.
It is recorded here as the reference point for what "10%" is protecting. It is
**not** the number this gate measures — see the next section.

### What this gate does and does not run

**The cross-host fleet gate is NOT run in this task.** It costs real AWS money
and this project's standing precedent (M1–M7) is that a fleet run is a separate,
explicitly owner-approved step. What runs here is `m5_gate all` — three nodes,
three services and the measuring client, all in one process on one 4-core dev
box, over real file-backed shared memory and real loopback UDP with all four
polling agents live per node.

That harness's own module doc calls its absolute output **smoke, not the gate**,
and this document repeats it: **no absolute throughput claim is made here.**
What the smoke harness *is* good for is precisely an A/B — both arms are
core-starved in exactly the same way, so the ratio between them is the signal
even though neither absolute is. The ≥90% bar is a **ratio** bar for that
reason.

A fleet confirmation of this ratio remains open work and is listed as such at
the bottom.

## The three measurement requirements

These are carried from earlier task reviews. Each exists because the obvious
benchmark would miss the thing that matters.

### (a) Measure with AND without the lock-free `sealing_epoch` fast path

M8's `SharedTransport` puts the handshake sessions, the group-key plane and the
rotation trigger behind one `std::sync::Mutex<KeyState>`, and **three busy-spin
agents now contend for it** (sender, receiver, consensus). This project has
measured that exact contention class before: `docs/notes/` and the v1 floor
analysis put a futex park at **8.8 µs against 29 ns for busy-spin**, and that
finding is what explained v1's throughput floor.

The T10/T17 reviews ruled deliberately **not** to pre-optimize this, so that
this gate could attribute any regression to it rather than guess. Both arms
are therefore measured:

* **arm A — mutex only** (the code as reviewed and merged through T17): every
  group seal takes the `KeyState` lock.
* **arm B — lock-free fast path**: the activated sealing epoch is published to
  an atomic under the lock and read without it on the steady-state seal path.

If arm A passes, arm B is a nice-to-have. If arm A fails and arm B passes, the
gate doc says so and the fast path is what ships.

### (b) The load must be CONCURRENT sender + receiver traffic

Recorded as a hard requirement by the T10 review: *"the throughput gate MUST
exercise CONCURRENT sender+receiver traffic, not sender-only sealing. A single-
agent benchmark cannot surface the KeyState mutex contention at all, and the
≤10% bar is the whole acceptance criterion."*

`TERM_MAP` is pairwise and ships alongside every commit gossip, so the consensus
agent takes the lock once per peer per commit advance, plus once for the
`COMMIT_POSITION` fan-out — while the sender agent is sealing `DATA` at line
rate and the receiver agent is opening the followers' `APPEND_POSITION` reports.
A three-node `m5_gate all` run drives all of that simultaneously by
construction. The results section records the per-arm evidence that it did.

### (c) AES-NI dispatch must be verified before any number is trusted

The T5 review measured **~1.2 µs per 1368-byte datagram ≈ 1.1 GB/s** for the
seal and flagged it: *"Sanity-check AES-NI dispatch is actually engaging BEFORE
the M8 throughput gate — this is the number the ≤10% bar rides on."* If the
`aes` crate's software fallback were in use, this gate would be measuring the
wrong system and a PASS would be meaningless. The verification and its method
are recorded in the results section.

## Known property to characterise (not to fix here)

Two earlier measurements say the same thing from different directions, and both
are about **liveness under stress, never safety** — no linearizability
violation has ever been observed with crypto on, across the full capstone set
(T15: `lin_v2`, `lin_partition_v2`, the multi-process SIGKILL crashtest, and the
elle consistency tier, all green with proven anti-vacuity).

* **T13 (deterministic sim):** the activation grace leaves a freshly elected
  leader unable to seal `DATA` or `HEARTBEAT` until its own epoch activates,
  because both are `Scope::Group`. Measured over 40 seeds of 30 s virtual time:
  at 20% packet loss the max term reached is **1.2 plain vs 3.7 crypto (~3×
  election churn)**; invisible below ~5% loss; commit throughput within 0–6% of
  plain at ≤20% loss.
* **T15 (capstones, matched A/B on this 4-core box):** with 4 CPU spinners,
  crypto failed a liveness bar **4 of 6** runs while cleartext failed **0 of 6**
  *at higher measured load*; isolated crypto still failed ~30%. The mechanism is
  **contention-amplified election/mint churn, not fixed latency** — uncontended,
  restart-to-active-epoch is ~250–350 ms and the mint itself ~5 µs.

**Owner ruling: run the gate first, then decide.** This document therefore
records whether the gate's own load surfaces the same cliff, and both
measurements alongside it. No mitigation is applied in this task, and in
particular no blind margin-widening — most T15 failures never reached their
wait budgets, so widening them would treat the wrong variable.

## Accepted residuals

All previously adjudicated during M8. Listed here so the gate record is
complete, not reopened.

1. **Any group-key holder can forge fan-out traffic as any node.** Inherent to
   seal-once-send-to-many: the group key is symmetric and shared, so it
   authenticates *membership*, not *sender identity*. A malicious cluster member
   is outside the threat model. (Pairwise traffic is Noise-IK and *is*
   sender-authenticated.)
2. **A removed node retains decryption until the next rotation.** Removal
   latches a rotation trigger, so the window is bounded by how fast the new
   epoch activates, not by the 1 h periodic interval — but it is non-zero.
3. **Cleartext headers leak positions, terms and datagram kinds** to a passive
   wire observer. Deliberate (spec §4): the receiver must demux by `kind` and
   locate by `position` before it can pick a key. The header is *authenticated*
   as AAD, not hidden.
4. **`read_frame_validated`'s bounds guard in `uc2_log` is `debug_assert!`-only**,
   so a corrupt length word is an out-of-bounds read in a release build. This is
   **pre-existing v2 code (introduced in `72f649b`, M1-era), OUT OF SCOPE for
   M8**, and confirmed as such during the T14 review. It deserves its own
   follow-up ticket against `uc2_log`.

## Measurement environment (read before the numbers)

Run **2026-07-29** on the shared development box, **not** a fleet: 4 vCPU, a
single machine running all **three nodes in-process** plus the client, so the
absolute `responses/s` is ~5× below the M5 *fleet* headline and is **not
comparable to it**. That is fine and deliberate — the gate is a **same-box
ratio** (crypto ÷ cleartext), and both arms carry the identical in-process
handicap. Two properties of this box actually make it a *conservative*
environment for the question the bar asks:

* **It is the worst case for the `KeyState` mutex** the T17 review flagged. On
  a fleet each node owns its cores; here all three nodes' twelve busy-spin
  agents fight for four cores, and three of them contend the one
  `std::sync::Mutex` per datagram. If lock contention were going to cost
  throughput, it costs *more* here than on any fleet. A small regression here
  bounds the fleet regression from above.
* **The box was not quiescent.** A concurrent `ansible-playbook` fleet-provision
  (SSH-driven, network-bound) and other sessions pushed the 1-minute load
  average from ~1 to ~12 across the six runs. `uptime` is recorded verbatim
  next to every run below so a reader can see it. Crucially the ansible load is
  network/SSH-blocked (~4 % local CPU each per `ps`), so it inflates *load
  average* without stealing CPU proportionally — which is why throughput did
  not collapse and the crypto arm stayed stable across the ramp.

Command (identical every run, only `--crypto` differs):
`cargo run -p uc2_node --release --example m5_gate -- all --secs 15 [--crypto]`.

## Results — cleartext control (arm 0)

Verbatim, three interleaved runs (`control, crypto` × 3). `responses/s` is the
gated metric; p50/p90/p99 are recorded but do not gate.

| run | load (1m,5m,15m) | responses/s | p50 | p90 | p99 |
|---|---|---|---|---|---|
| control 1 | 0.85, 3.19, 2.29 | **168 127** | 8.315 ms | 16.114 ms | 66.126 ms |
| control 2 | 7.22, 4.49, 2.75 | **335 698** | 8.454 ms | 14.893 ms | 85.656 ms |
| control 3 | 10.89, 5.63, 3.19 | **305 232** | 9.601 ms | 16.941 ms | 91.685 ms |

**Median: 305 232 responses/s.** `control 1` is a settling/warm-up outlier —
it ran first, immediately after the quiet-window wait, with the box still
draining a prior load burst (5-min avg 3.19) and cold caches; its `168 127` is
the *lowest* value at the *lowest* nominal load, the opposite of a
contention-starved run. The pre-committed **median-of-three** exists precisely
to discard exactly one such outlier, and does.

## Results — encrypted, mutex only (arm A — the merged code, no fast path)

| run | load (1m,5m,15m) | responses/s | p50 | p90 | p99 |
|---|---|---|---|---|---|
| crypto 1 | 4.14, 3.80, 2.50 | **287 208** | 10.797 ms | 18.792 ms | 82.641 ms |
| crypto 2 | 8.95, 5.01, 2.95 | **293 418** | 10.019 ms | 16.728 ms | 99.877 ms |
| crypto 3 | 11.72, 6.07, 3.37 | **281 533** | 10.871 ms | 19.038 ms | 75.301 ms |

**Median: 287 208 responses/s.** The encrypted arm is notably *stable* across a
load ramp from ~4 to ~12 (range 11.9 k, ±2 %), which is the behaviour of a
system whose throughput is bounded by its own busy-spin agents rather than by
the ambient noise.

**Crypto-plane fail-closed check (in-window deltas, all three crypto runs):**
`auth_failed = 0`, `replay = 0`, `unknown_peer = 0`, `unknown_epoch = 0`,
`cleartext_peer = 0` on **every** node, and `seal_failures = 0` on **both
followers**, every run. This is the load-independent evidence that the
encrypted arm is a *working* system, not a degraded one: no traffic failed the
crypto plane during the measured window. Both followers sealing (~10–45 k
seals each) while the leader seals (~1.6–2.3 M) is the T10-review concurrency
evidence — the load drove both directions of the plane at once, which
replication could not have done otherwise.

**The leader's in-window `seal_failures` (~1.0–1.2 M per run) are expected and
benign.** A node reports its durable/append position to `cfg.leader`, and on
the leader that address is *itself*; a node holds no pairwise Noise session
with itself, so every self-addressed `APPEND_POSITION`/`STATUS` fails to seal
with `NoSession` and is counted. This is a **pre-existing v2 self-send** — the
receiver has always addressed those reports to `cfg.leader` in cleartext too;
wire crypto only made it *visible* by counting the fast-fail. It is harmless
(the leader's own position reaches its commit ranking in memory, never over the
wire — the T15 linearizability capstones pass with crypto on) and symmetric
across both arms (cleartext sends the identical datagram, uncounted), so it does
not move the ratio. Suppressing the self-addressed report is a small efficiency
win filed as a **post-M8 follow-up**, not a correctness fix. See
`uc2_net::receiver` (`seal_and_send(self.cfg.leader, …)`) and the
`print_crypto_observability` doc in `m5_gate.rs`.

## Results — encrypted, lock-free fast path (arm B)

**Not built — not needed.** The pre-committed plan (§a above) said: *"If arm A
passes, arm B is a nice-to-have."* Arm A passed (below). The `KeyState` mutex —
measured here in its worst case (three busy-spin agents, four shared cores) —
did **not** produce a bar-failing regression, so the lock-free `sealing_epoch`
fast path is **deferred as a documented optimization rather than shipped**.
This honours the measure-first discipline: it was deliberately not
pre-optimized, it was measured, the mutex was fine at scale, and no complexity
was added on speculation.

## AES-NI verification

Load-independent, and decisive. `uc2_crypto/examples/seal_bench` on a 1368-byte
datagram, hardware build vs a forced-software build
(`RUSTFLAGS="--cfg aes_force_soft --cfg polyval_force_soft"`):

| build | seal | throughput | open (by diff) |
|---|---|---|---|
| **hardware (AES-NI)** | **1 333.6 ns/datagram** | **1.06 GB/s** | 1 217.5 ns |
| forced software | 10 949.0 ns/datagram | 0.13 GB/s | 11 269.0 ns |

**8.2× slower in software → hardware AES-NI dispatch is confirmed engaging.**
The box exposes `aes` + `pclmulqdq` on all four cores. The hardware seal cost
(1.33 µs) matches the T5 review's ~1.2 µs measurement, so every throughput
number above is of the real hardware-accelerated system, not an accidental
software-fallback build.

## Adjudication against the pre-committed rule

> **PASS iff encrypted median ≥ 90 % of the cleartext median.**

* cleartext median: **305 232** responses/s
* encrypted median: **287 208** responses/s
* ratio: **287 208 / 305 232 = 0.941**, i.e. a **5.9 % regression**

**0.941 ≥ 0.90 → PASS**, with ~4 points of margin, by the rule written down in
commit `17baf9d` before any arm ran. The bar was not adjusted after seeing the
data, and all six runs are printed verbatim above regardless.

**Honesty about the strength of this PASS.** The end-to-end ratio carries
measurement noise (a non-quiescent shared box), so it is corroborated — not
carried alone — by two load-independent results that a busy box cannot distort:
the microbenchmark (a bounded 1.33 µs seal, AES-NI confirmed) and the perfectly
clean fail-closed counters (zero dropped/failed crypto traffic in every window).
Together these say the seal cost is small, the encrypted plane is a working
non-degraded system, and the same-box overhead is ~6 % in a *pessimistic*
contention environment. **The definitive absolute-throughput number is the
cross-host fleet A/B** (below, owner-approved separately) — as it was for M5,
whose headline was itself a fleet number. This local gate establishes the
overhead is small and the bar is met; the fleet gate would establish the
absolute figure on real hardware and real RTT.

**Latency note (reported, not gated):** crypto p50 ran ~2 ms above cleartext
(~10.5 vs ~8.5 ms). Both are dominated by scheduling latency on an
oversubscribed 4-core box (the M5 *fleet* p50 was 0.6 ms), not by cryptography;
the ~2 ms delta is not a meaningful signal for the real system and does not
retroactively become part of a bar that was pinned as throughput.
