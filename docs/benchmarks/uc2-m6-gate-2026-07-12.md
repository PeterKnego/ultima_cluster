## What the gate measures

Spec §9's milestone table
(`docs/superpowers/specs/2026-07-09-uc-v2-aeron-shaped-smr-design.md`), verbatim:

| # | deliverable | gate |
|---|---|---|
| M6 | snapshots, learners, purge, ops | learner join under load; purge safety; reconstruction under load |

M6 is the milestone that makes **journal purge safe**. Everything before it kept
the entire log forever; M6 lets a node drop the log prefix below a
service-built snapshot, and proves that a node which has fallen below that floor
— a crashed-and-restarted service, a fresh learner, a cold-started node — still
converges to the correct committed state by **installing a snapshot and
tail-replaying**, never by reading the purged prefix. Purge is **OFF by default**
(`PurgePolicy::Disabled`); it becomes safe only because snapshots back it.

The three claims, and how each is proven:

1. **Purge safety / reconstruction under load** — proven at the strongest level:
   the L3 WGL lincheck capstone, re-run with purge on.
2. **Learner join under load** — proven for correctness at the loopback level
   (the `learner` integration test + the `m6_gate` learner-join scenario); the
   fleet number (join completes with < 10 % commit-rate dip) is the official
   figure, recorded here after the fleet run.
3. **Ops** — the observability band, runbook, and the closed prefill decision
   (M6 Task 9); not a throughput number, so not gated here — see
   `docs/ops/uc2-runbook.md`.

## Correctness proofs (local, green)

### L3 lincheck under purge + snapshot churn — the milestone's heart

`uc2_node/tests/lin_v2.rs::linearizable_under_purge_and_snapshot_churn`. The
same seeded workers + WGL checker as the M5 failover capstone, but **every node
runs snapshot-backed purge** (16 KiB journal segments, a 32 KiB snapshot
cadence, `PurgePolicy::BelowSnapshot { slack_bytes: 0 }`) and the fault mix
gains a third 1-in-3 arm: **crash a random follower's service**. Under purge that
follower's fresh empty service can no longer tail-replay from the journal (the
leader purged the prefix it needs), so the node reconstructs it via a **snapshot
install + tail-replay** (Task 5). The recorded history must be WGL-linearizable.

Non-vacuity is asserted, not assumed: the test fails unless purge actually
advanced the archive floor during the run (`max_archive_first_base > 0`), so the
below-floor reconstruction path was genuinely exercised. (This assertion caught
an early tuning where 128 KiB segments never filled at the workload's data
volume — `purge_floor` stayed 0 and the "below-floor" fault degenerated to a
plain tail-replay. Shrinking segments below the snapshot interval fixed it.)

Bars (same as the failover capstone): ≥ 80 % `Ok`, `check_register ==
Linearizable`, ≤ 120 s, across seeds `0x1107` / `7` / `99`. Result:

| seed | faults (follower-svc) | ops | ok | purge_floor | elapsed | verdict |
|------|-----------------------|-----|-----|-------------|---------|---------|
| 0x1107 (4359) | 29 (13) | 883 | 874 | 24 288 | 36.0 s | Linearizable |
| 7    | 5 (4)   | 873 | 873 | 24 096 | 6.0 s  | Linearizable |
| 99   | 12 (2)  | 813 | 811 | 24 096 | 15.7 s | Linearizable |

`purge_floor > 0` on every seed = purge dropped a real journal prefix and the
follower rebuilt from a snapshot, under churn, staying linearizable.

## `m6_gate` sandbox smoke (NOT the gate)

`cargo run -p uc2_node --release --example m6_gate -- all --secs 6 --cycles 5`.
Three voters + one pre-provisioned learner + services + a background write-load
driver, all in-process (real file-backed shmem), purge on. Verbatim console
(one dev box, core-starved across ~16 polling agents + services + the driver):

```
== uc2 M6 gate: SMOKE (local, in-process; 3 voters + 1 learner + services + load) ==
leader elected: n1

== M6 gate smoke results ==
  [PASS] learner-join — joined=true in 0.10s (budget 60s), baseline=148905 commits/s,
         during-join=82674 commits/s, dip=44.5% (window 0.10s too short to gate on this
         box — informational), learner_led=false, load_committed_max=14091
  [PASS] purge-cycle — 5 cycles: every follower-service reconstruction converged
         (worst 0.0s / 10s budget), reads monotonic (last=14102), purge_fired=true
RESULT: PASS (smoke) — both M6 scenarios held locally.
```

**Honest reading of the smoke numbers:**

- **learner-join**: the learner joins and never leads, and commit keeps
  advancing throughout — the pass criteria that ARE meaningful on this box. The
  `< 10 % dip` is **not** gated here: the learner's register state is trivial, so
  its snapshot install is instant and the join completes in ~0.1 s — far too
  short a window to measure a commit rate against (the printed dip is pure
  scheduling noise, flagged "informational"). The dip is a **fleet** metric: only
  under sustained fleet load does the join take real wall-clock time and the
  10 % bar become measurable.
- **purge-cycle**: this one IS meaningful on the box — `purge_fired=true` proves
  the archive floor advanced, so each follower-service crash reconstructed from a
  **snapshot install** (below-floor), every reconstruction converged well inside
  the 10 s budget, and linearizable reads stayed monotonic and matched the write
  stream across all 5 cycles (zero committed-value divergence).

## Multi-process validation (real separate processes, real UDP — local)

Between the in-process smoke and the fleet run there is a stronger local proof:
`bench-infra/scripts/m6_fleet_gate.py --local` drives **four real separate
processes** (3 voter nodes + 1 learner, each its own OS process, each with its
own node + service process) over **real loopback UDP** — not the in-process
`all`. It runs the exact same scenario logic the fleet run uses (`--fleet`),
observing every node only through `m6_gate probe` (reads that node's local cnc)
and driving load + the divergence guard through `m6_gate loadclient` on the
leader host. This validates the orchestrator itself and exercises genuine
cross-process reconstruction over the wire. Representative run (one dev box,
core-starved across ~9 processes):

```
[m6-gate] == M6 LOCAL (4 procs, loopback UDP) gate ==
[m6-gate] leader elected: node1
[m6-gate] [PASS] learner-join — joined=True in 0.00s (budget 60s), baseline=139283 commits/s,
          during-join=127754 commits/s over 5.0s, dip=8.3% (gate <10%), learner_led=False
[m6-gate] [PASS] purge-cycle — 4 cycles: every follower reconstruction converged
          (worst 0.11s / 10s), purge_fired=True
[m6-gate] RESULT: PASS
```

Both scenarios PASS with the fleet thresholds (`dip < 10%`, converge `< 10 s`)
across repeated runs (dip 7–8%). Two things the in-process smoke could NOT show
now hold: the commit-rate dip is measured over a fixed 5 s window spanning the
join and stays **under the 10% gate** (real cross-process, so the number is
meaningful, not noise), and each follower-service reconstruction converges in
**real cross-process time** (~0.11 s, vs the in-process 0.0 s) with `purge_fired`
confirming the rebuild was a below-floor snapshot install. The ~8% dip is a
core-starvation artifact (4 nodes + services + driver share the box's cores); on
the fleet's one-role-per-host budget it should be far smaller.

## Fleet result — **PASS** (2026-07-13)

Run over a real 4-host AWS fleet: **3 voters + 1 learner host**, all
`c6id.2xlarge`, `us-east-1`, one placement group so learner-join bandwidth is
real cross-host UDP (not loopback). Each host runs exactly one role
(`m6_gate node|service|learner`, systemd-run-launched), NVMe journals under
`/opt/bench`, fdatasync on, purge on (`BelowSnapshot`). The
`bench-infra/scripts/m6_fleet_gate.py --fleet` orchestrator drove both
scenarios, observing every node only through `m6_gate probe` (that node's local
cnc) and driving load + the divergence guard through `m6_gate loadclient` on the
leader host.

```
[m6-gate] == M6 FLEET gate ==
[m6-gate] leader elected: node0
[m6-gate] [PASS] learner-join — joined=True in 1.32s (budget 60s), baseline=267076 commits/s,
          during-join=264626 commits/s over 5.0s, dip=0.9% (gate <10%), learner_led=False
[m6-gate] [PASS] purge-cycle — 5 cycles: every follower reconstruction converged
          (worst 2.80s / 10s), purge_fired=True
[m6-gate] RESULT: PASS
```

| scenario | result | headline number | gate | verdict |
|---|---|---|---|---|
| **learner-join** | joined in **1.32 s** (budget 60 s), never led | commit-rate dip **0.9 %** (267 076 → 264 626 commits/s over a fixed 5 s window spanning the join) | dip **< 10 %** | ✅ PASS |
| **purge-cycle** | 5 cycles, `purge_fired=True` every cycle | worst below-floor reconstruction converged in **2.80 s** | converge **< 10 s**, zero committed-value divergence | ✅ PASS |

**Honest reading:**

- **learner-join**: on the fleet's one-role-per-host budget the join takes real
  wall-clock time (1.32 s vs the loopback ~0 s), so the 5 s measurement window is
  fully populated and the **0.9 % dip is a real, gateable number** — an order of
  magnitude under the 10 % bar, and far below the ~8 % local core-starvation
  artifact (as predicted). The learner is never in the quorum (`learner_led=False`)
  so a correct join is invisible to commit progress — the dip being ~0 is exactly
  the expected shape.
- **purge-cycle**: `purge_fired=True` on every one of the 5 cycles proves the
  archive floor advanced, so each follower-service crash reconstructed from a
  **below-floor snapshot install + tail-replay** over the wire — not a journal
  tail-replay. Every reconstruction converged well inside the 10 s budget (worst
  2.80 s), and the `loadclient` linearizable-read guard saw zero committed-value
  divergence across all cycles (it exits `1` on any divergence; the run exited 0).

The role binaries are thin one-role-per-host wrappers (`m6_gate node|service|learner`,
systemd-run-friendly, park forever). The gate binary exits `1` on an honest FAIL,
so it composes in CI / the fleet driver — this run exited `0`.

**M6 GATE PASSED.** Fleet torn down after the run (`terraform state list` empty).
