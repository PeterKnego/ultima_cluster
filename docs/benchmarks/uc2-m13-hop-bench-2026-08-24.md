# M13 hop-isolation bench — where the remote path's throughput goes (2026-08-24)

**Status:** measurement, no bar. Run autonomously on 2026-08-24 as the
opening move of M13 (remote-path performance). Every number in the fleet
section comes from one provisioned fleet, destroyed and verified empty
afterwards; the dev-box section is a smoke and is labelled as such.

## Why this bench exists

M12 ended with three numbers that did not compose into a mechanism:

- the cluster commits ~1.4 M commands/s from one shmem `Engine`
  (`uc2-m12-gate-2026-08-22.md`, network-budget section), so the backend is
  not the limit;
- ONE `RemoteClient` over ONE TCP connection through the edge reached
  ~140 k resp/s after the batching fix (row 2), ~0.1× the direct arm;
- N such connections aggregated near-linearly to N = 4 (451 k resp/s) and
  then collapsed 30× at N = 8 (edge saturation ladder + clean-discipline
  re-run).

Those runs measured the whole path end to end, so "which hop pays the
~10×" was an inference from CPU attribution, not a measurement. This bench
measures each hop **alone** by putting a dummy sink behind it and a minimal
driver in front of it, then composes hops pairwise so each hop's cost is a
subtraction.

```text
[RemoteClient] ─TCP─▶ [Edge] ─shmem Engine─▶ [node] ─▶ consensus ─▶ [service]
     hop 3             hop 2         hop 1
```

## Harness

`uc2_gateway/examples/hop_bench` (one binary, one role per process; every
load role prints one `RESULT {json}` line). Fleet driver:
`bench-infra/scripts/m13_hop_bench.py`; dev-box smoke: `hop_bench local`.

| role | what it is | isolates |
|---|---|---|
| `dummy-node` | node-shaped process over a **real** instance dir (`cnc2.dat`, `ingress.ring`, `query.ring`, both egress broadcasts, same `MAX_MSG` as `uc2_node::create_rings`), cnc page marked `LEADER \| CAN_SERVE`, one busy-poll thread that pops every ingress/query record and publishes exactly one position-keyed `MSG_V2_RESPONSE` for it; payload discarded, position synthesised from the aligned frame length | hop 1's sink: a node with an infinitely fast backend, no admission window |
| `engine-load` | N independent `uc2_client::Engine` attachments (one sender + one poll thread each; poll thread yields, never sleeps) | hop 1's driver |
| `edge` | the real `uc2_gateway::Edge`, same config shape the M12 fleet edge used (`status_interval` 200 ms, `request_timeout` 30 s) | hop 2 |
| `blaster` | raw remote-protocol v1 client: HELLO, pre-encoded SUBMITs in batches of ≤ `--batch` frames per `write`, credit window off `ResponseMeta`/`STATUS`, buffered RESPONSE parsing; two threads per connection sharing three atomics, no mutex on the hot path, no `Ticket`, no pending map, no reconnect | hop 2's driver; against `dummy-edge` it is the raw framed-TCP floor of the box pair |
| `remote-load` | N real `RemoteClient`s, each driven the way `m12_gate client-remote` drives one (a submit loop paced by `submit()` blocking on credits, 4 waiter threads) | hop 3's driver |
| `dummy-edge` | TCP server that answers HELLO_OK and then one RESPONSE per SUBMIT/QUERY immediately, batching every frame one `recv` delivered into one `write` (the real driver's discipline) | hop 3's sink |

Payload is 64 raw bytes everywhere (no bincode, no session envelope — the
sinks discard it; the real-cluster arms run the raw state machine with the
envelope off so the bytes are the same there too). Latency is
send-to-response on the driver, drain-inclusive elapsed, HdrHistogram.

CPU is sampled on the server host, on the sink/edge **process** (percent of
ONE core: 100 = one full core) and on the client host, inside each point's
run window, exactly as the M12 edgesat row did (`/proc/stat` +
`/proc/<pid>/stat` deltas, `mpstat` when present).

## Fleet results (2026-08-24, 4× `c6id.2xlarge`, us-east-1, destroyed + verified afterwards)

Same sink, same wire as B. `RemoteClient` caps at **171 k/s per

- **N = 4 = 465 k/s at 84% client host** is the number M12's edgesat ladder
  reported at N = 4 *through the real stack* (451 k). That rung was the
  client host running out of cores for four `RemoteClient`s — not an edge
  ceiling, and M12's own driver flagged it "client-tainted".
- N = 8 → 16 jumps **super-linearly** to 1.2–1.4 M/s with the host pegged:
  once a `RemoteClient` cannot get the CPU to drain its window immediately,
  the window stays closed, its batching engages and it becomes ~2.6× more
  efficient per core. The lever exists in the code; nothing pulls it at
  ordinary load.

Driven raw, **one connection through the shipped edge relays 1.42 M/s** —

## The collapse, diagnosed: the MPSC ingress ring convoys under CPU oversubscription

`--arms diag` (same fleet, blaster → edge(window 65536) → dummy-node, 12 s
per rung) samples every edge thread's CPU and current syscall for 3 s
mid-rung (`bench-infra/scripts/thread_sample.sh`) and echoes the edge's own
per-second counters:

| rung | resp/s | driver thread | reader threads | `backpressure/s` | `retries/s` |
|---|---:|---|---|---:|---:|
| 4 × 1024 | 1,720,426 | **99.0%**, running | 63–68% each, mostly in `recvfrom` (45) | 0 | 0 |
| 6 × 1024 | 1,477,494 | 94.7% | 54–57% each, running | 0 | 0 |
| **8 × 128** | **4,090** | **7.3%, parked in `futex_do_wait`** | **81–97% each, user space (no syscall)** | **0** | 0 |
| 8 × 1024 | 17,948 | 9.0% | 82–94% each, user space | 0 | 0 |

Healthy rungs: the driver — the one thread that drains the shared `Engine`
and writes every response — is pinned at ~100% (that is the ~1.9 M/s
aggregate knee), readers wait on their sockets. Collapsed rungs: the edge
reports **zero backpressure and zero retries** — the credit ladder never
runs — while the readers spin **in user space** and the driver has nothing
to do. The readers' only user-space spin is inside the shared-memory MPSC
ingress ring's producer:

```rust
// uc_protocol/src/ring/mpsc.rs (before this branch), MpscProducer::try_write
// Publish in claim order: wait until our predecessor has advanced
// `publish_position` up to our slot start, then bump it ...
while header.publish_position.load(Ordering::Acquire) != claim_pos {
    std::hint::spin_loop();
}
header.publish_position.store(target_pos, Ordering::Release);
```

Publication is serialized in claim order across **every producer thread**.
A producer that is preempted between its `claim_position` CAS and its
`publish_position` store stalls every producer that claimed after it — and
those producers spin at 100% on the very cores the preempted one needs.
The convoy is self-sustaining: the more producers spin, the longer the
victim waits, the more producers pile in behind it. Once formed, the ring
moves a few thousand records per second with every core busy, the driver
starves, the clients' windows never reopen, and the client host goes idle —
exactly the M12 picture.

That is why the trigger is the **number of connections** and nothing else:
the server host has 8 vCPUs; sink + driver + 6 readers = 8 threads, every
producer always has a core, no preemption inside the claim→publish window;
8 readers = 10 threads, preemption there becomes routine. The edge's
window, the node's admission window, the per-connection credits and the
client implementation are all irrelevant to it — F showed the collapse at
2,048 total outstanding, well under the admission window, and C/E showed
it with `RemoteClient` and with the raw blaster alike.

**Reproduced with no edge and no TCP, on the 4-vCPU dev box** — N local
`Engine`s (one producer thread each, plus a poll thread) into one dummy
node (`convoy-local.sh`, inflight 256, 4 s):

| engines | busy threads on 4 vCPU | resp/s |
|---:|---:|---:|
| 1 | 3 | 1,658,038 |
| 2 | 5 | 1,531,127 |
| 4 | 9 | **5,589** |
| 8 | 17 | 1,229 |

So this is not a gateway defect. It is a defect in `uc_protocol::ring::mpsc`
that any N shmem clients on a busy host can trigger; the gateway is simply
the first thing in the tree that put eight producer threads on one ingress
ring on a host that had other work. M12's root-cause note
(`docs/notes/uc2-m12a-edge-flow-control-gap.md`: "per-connection credits
with no global budget tied to the admission window") described a real gap
in the spec's flow-control design, but it is **not** what collapsed the
fleet. The operating-envelope rule in `run-a-gateway.md` ("sum of client
inflight < `max_inflight`") does not protect against this either — F at
8 × 256 was inside it.

### Mitigation experiment: bounded spin, then yield (`d8a168d` on this branch)

The smallest change that breaks the feedback loop: after
`PUBLISH_SPINS_BEFORE_YIELD = 128` spins the waiter calls
`std::thread::yield_now()`, handing its core to whoever is runnable — which
includes the preempted predecessor. The fast path (predecessor already
published) is untouched. 73/73 `uc_protocol` tests pass (`cargo test -p
uc_protocol`); no new test was added — this is a scheduling-behaviour
change, verified by the reproduction:

| engines (dev box, 4 vCPU) | pure spin | bounded spin + yield |
|---:|---:|---:|
| 1 | 1,658,038 | 1,791,834 |
| 2 | 1,531,127 | 1,838,373 |
| 4 | **5,589** | **160,604** (29×) |
| 8 | 1,229 | 146,203 (119×) |

Degradation instead of collapse — but 11× under the single-engine number,
so a mitigation, not the fix. The structural fix is the one Aeron's
many-to-one ring buffer uses: producers commit their own record
independently (the atomic-after-write length prefix the rest of UC's
framing already relies on), the single consumer walks records in claim
order and stops at the first uncommitted one, and **no producer ever waits
for another**. A preemption then costs one thread's scheduling latency at
the consumer, not a convoy. That changes the ring's publish invariant
(`publish_position` goes away or becomes advisory), touches the wait/signal
handle, and needs the ring tests plus the still-open loom-on-rings item —
M13 design work, not an afternoon. Fleet numbers for the mitigation are in
the next section.

## What this means for M13

The per-hop budget of the remote path, on one `c6id.2xlarge` pair, one
connection, 64 B payload (fleet numbers above):

| stage | resp/s | who pays |
|---|---:|---|
| shmem `Engine` → node (hop 1, null backend) | 2.8 M | — |
| real cluster, direct `Engine` (G) | 1.9 M | consensus + service |
| raw TCP, two hosts, one connection (B) | 7.4 M | — |
| raw client → **real edge** → null node (D) | 1.42 M | edge reader + driver, 2 cores |
| raw client → real edge → **real cluster** (F) | **1.14 M** | the whole shipped path minus the client |
| **`RemoteClient`** → null edge (C) | **0.17 M** | the client's own structure |
| `RemoteClient` → real edge → real cluster (M12 row 2) | 0.14 M | = C, minus 15% |

Ranked by what it is worth fixing:

1. **`RemoteClient` is the remote path's bottleneck — by 7×.** One
   connection through the shipped edge into the shipped cluster carries
   1.14 M resp/s at p99 1.3 ms when the client does not get in the way. The
   client caps at ~170 k: one `write` per `submit` (its batching only
   engages when the window is closed, which a healthy edge never lets
   happen), one state lock across submit + write + every received frame,
   and a futex wake per ticket — ~7 futex + 1 `sendto` per request. The
   blaster is the existence proof of the target: two threads per
   connection, three atomics, batched writes, buffered reads, and it is
   50× faster against the same sink. M13's client work is a redesign of
   the hot path, not a tuning pass: a dedicated writer that coalesces
   whatever is queued (flush-on-empty, no timer), completion delivery that
   does not take the state lock per frame, and a completion API that does
   not cost a channel per request (a batch/callback path beside `Ticket`).
   The fleet driver, the crashtest capstone and every user of
   `submit()`/`Ticket::wait` stay valid — this is under the API.

2. **The MPSC ring's publish-order spin is a real defect and the actual
   cause of the M12 collapse** — not the credit design. It lives in
   `uc_protocol::ring::mpsc`, is reachable by any N shmem producers on a
   busy host, and has a cheap mitigation (`d8a168d`, measured below) and a
   known structural fix (independent per-record commit, consumer stops at
   an uncommitted record). The structural fix belongs in M13 with the ring
   tests extended for preemption inside the claim→publish window and the
   loom-on-rings item finally cashed in. The M12 gap note and
   `run-a-gateway.md`'s operating envelope need correcting: the envelope
   rule does not prevent this, and CPU containment (`CPUQuota=`) makes it
   *more* likely, not less — it starves the preempted producer harder.

3. **The edge is fine to ~1.9 M/s aggregate and then it is one thread.**
   The driver drains the single `Engine` and writes every response; at the
   knee it is at 99% and the readers idle. Past that, more connections buy
   nothing and (on a co-located host) start competing with the node's
   agents — F at N=4 shows p99 growing as the leader host fills. If M13
   wants the edge above ~2 M/s the shape is N drivers over N `Engine`s (the
   hop-1 arm showed two engines fan in at 4.5 M/s), but that is a
   second-order item behind 1 and 2; today the edge out-runs the cluster.

4. **The spec's cross-connection credit budget (§4.2) is still unbuilt**,
   and still worth building — it is what makes overload *graceful* once
   the convoy is gone (bounded queueing at the edge instead of the
   reactive halve/relax ladder). It is not what was collapsing the fleet,
   so it moves from "the M13 fix" to "M13's flow-control item", to be
   measured with this harness after 2 lands.

5. **Row-2 re-spec.** With the client fixed, the meaningful gate is the
   one this bench already runs: aggregate through the edge vs the direct
   arm on the same generation (F/G here: 1.43 M vs 1.91 M at N=2 = 0.75×
   with the raw client), plus a per-connection number. The 0.8× bar was
   not mis-specified after all — it was measured with a client that could
   not reach it.

### The mechanism, from `strace -c` (dev box, 1 connection → `dummy-edge`, 3 s, inflight 1024)

Same sink, same wire, same payload; only the driver differs. Counts are
under `strace`, which taxes every syscall, so the *rates* are depressed
(the client that makes 8 syscalls per request suffers ~200× more than the
one that makes 0.03) — the per-request ratios are the fact:

| driver | requests | `sendto` | `recvfrom` | `futex` | syscalls / request |
|---|---:|---:|---:|---:|---:|
| `RemoteClient` | 13,894 | 13,895 = **1.00 / req** | 4,661 (3 resp / recv) | **99,981 = 7.2 / req** | **8.5** |
| `blaster` | 2,944,895 | 46,017 (64 frames / write) | 45,105 (65 frames / recv) | 0 | **0.03** |

95% of `RemoteClient`'s syscall time is `futex`. A second run with
`-e trace=futex,sendto,recvfrom` attributed per thread (5,949 requests):

| thread | `futex` / req | other |
|---|---:|---|
| submitter (the caller's thread running `enqueue` → `pump`) | 2.1 | exactly 1 `sendto` per request |
| `uc2-remote-rx` reader | 3.2 | 1 `recvfrom` per ~3 responses |
| the 4 ticket waiters, combined | 1.8 | (the `Ticket::wait` itself) |

So per request the client pays one `write` **and** ~7 futex operations:

1. **One `write` per `submit`.** The batching fix (`74cf53b`) coalesces
   frames the credit window is *holding*; with an edge that answers fast
   enough, the window is open at every `submit`, `pump` finds exactly one
   unsent frame and writes it. The batching fix helped the deep-window
   fleet run precisely because the window was closed there; it cannot help
   the case where the client is the slower side. The blaster batches by
   construction (up to 64 frames per write).
2. **The state lock is taken per frame on both sides.** `on_frame`
   (`uc2_remote/src/client.rs:854-1022`) locks `Inner.state` once per
   received frame, `enqueue` locks it once per submit and holds it across
   the `write`; every hand-off between the two threads is a futex pair.
3. **Per-ticket wake-ups.** Each completion is a `SyncSender::send` to that
   ticket's channel (a futex wake) plus the `Condvar::notify_all` per read
   batch; each `Ticket::wait` is a futex wait.

The blaster's per-connection design — two threads, three atomics, no lock
on the hot path, batched writes, buffered reads — is the existence proof
that the wire, the edge and the kernel are not the limit at this scale.

### Variant: can the existing client be driven harder? (`remote-load --senders N`)

If the one-`write`-per-`submit` behaviour were the whole story, several
caller threads on ONE `RemoteClient` would keep its window closed, engage
the batching it already has, and lift the number. Dev box, 1 connection →
`dummy-edge`, 3 s, inflight 1024 (`senders-exp.sh`):

| caller threads on one `RemoteClient` | resp/s | p50 ms |
|---:|---:|---:|
| 1 (the `m12_gate` shape) | 50,083 | 12.5 |
| 2 | 55,021 | 12.2 |
| 4 | 56,339 | 12.5 |
| 8 | 55,977 | 12.8 |
| blaster, same sink, same moment | 3,663,476 | 0.18 |

+12% and flat. The batching does engage, and the extra callers then pay it
straight back contending the state lock with each other and with the reader.
The ceiling is the client's *structure* (one lock across submit, write,
per-frame receive, and per-ticket wake-up), not the way it is driven — a
user cannot configure or thread their way out of it.
