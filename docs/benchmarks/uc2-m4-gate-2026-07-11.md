# uc2 M4 gate — leader failover (elections + term map + truncation)

**Date:** 2026-07-11

> **⚠️ THIS IS A SINGLE-HOST LOOPBACK MEASUREMENT ON A 4-vCPU SANDBOX.**
> The fleet confirmation (3 × c6id, one node per host, real LAN) is appended
> later — but unlike the M2/M3 throughput bars, **loopback is REPRESENTATIVE for
> this gate**, and the reasoning is load-bearing (see "Why loopback is
> representative" below).

The M4 gate is the **failover proof**: with a static-membership 3-node cluster,
killing the serving leader must produce a new serving leader **in under a
second** with **zero committed loss**, and the deposed node must rejoin cleanly
when restarted. Per spec §9 the gate is **two halves**: (1) the L1 simulator +
partition lincheck stay green under scripted adversity and seeded fuzz, and
(2) the measured failover distribution is sub-second with no loss. Both halves
are recorded here; both pass.

## What the gate measures

Spec §5–§6 / §9: the **detection → election → NewTerm-commit → serving** path.
Each iteration boots to a single serving leader, drives ~2 s of admission-paced
load so the leader is killed with a real committed history behind it AND an
uncommitted inflight tail ahead of its commit, then `crash()`es it and times two
metrics from the single instant of the kill:

- **kill → serve** — wall time until a survivor's `can_serve()` turns true. A
  survivor's follower-liveness timer (150–300 ms, randomized per node) expires,
  it wins a vote (votes persisted-before-answered), opens its term with a
  **NewTerm frame** at the committed base, and — per the §5.4.2 serving gate —
  only turns `can_serve` true once that NewTerm frame is **quorum-committed**.
- **kill → commit-advance** — wall time until a survivor's commit counter moves
  **past the pre-kill committed floor**. Because the serving gate is exactly "the
  NewTerm frame reached quorum commit," this is the *same event* as kill→serve
  (see the note under the output — the two columns are identical by
  construction, which is itself a correctness statement: a node never serves
  before it has quorum-committed in its new term).

**Zero committed loss** is asserted every iteration: the committed floor is the
`min` of the two survivors' commit counters captured just before the kill, and
after failover every survivor's commit must still be ≥ that floor (commit never
regresses below quorum-durable history). The killed node is then restarted from
its **same dirs on its same port**; it recovers durable state, adopts the
current term as a follower, and **truncates any divergent inflight tail** it had
made durable before the crash — the next iteration runs on a healthy 3-node
cluster.

Verdict: **PASS** iff every iteration served in < 1 s AND no committed byte was
ever lost.

## Why loopback is representative (unlike M2/M3)

M2/M3 measured **throughput and commit latency**, which are set by fsync speed,
NIC, and core count — all artifacts the sandbox distorts, so those gates deferred
their verdict to the fleet. M4 measures **failover time**, which is dominated by
the **randomized 150–300 ms election timeout**, not by the wire. Loopback RTT is
sub-µs; a real LAN adds only a few hundred µs of detection/vote round-trips on
top of a ~200 ms timeout — i.e. **< 0.2 %** of the measured interval. The
sandbox's fsync being ms-scale slightly *inflates* the NewTerm-commit tail here
(a faster NVMe fsync would make the fleet number *lower*), so the sandbox
measurement is a conservative upper bound on the metric the gate cares about. The
fleet run confirms the absolute detection timing on a real NIC; it does not
change the shape of the result.

## The sim evidence (spec §9 half one — L1 simulator + fuzz)

The simulator (`uc2_sim`) drives the real `ElectionSm` + reconcile logic through
a deterministic virtual-time `World` and, after **every** event, checks five
safety invariants against ground truth:

- **inv1 — election safety:** at most one leader ever opens a given term.
- **inv2 — term-map prefix consistency:** every node's committed-position term
  boundaries are a prefix of the authoritative committed lineage (content
  identity is the term at a position; §6).
- **inv3 — commit monotonicity:** a node's commit never regresses (except the
  exempt, expected reset on restart).
- **inv4 — committed-never-truncated:** a node never truncates below its own
  committed high-water.
- **inv5 — leader completeness (phantom-commit guard):** a commit only advances
  ground truth when a **genuine byte-content quorum** holds those bytes — the
  order-statistic commit is checked for *every* leader, including a stale leader
  of a superseded term, so a delayed report can never manufacture a commit no
  quorum backs.

**Scripted nasties** (`uc2_sim/tests/scenarios.rs`), each asserting the
invariants held AND the expected outcome:

- `quiet_cluster_elects_exactly_one_leader_and_commits` — clean boot to one
  leader.
- `split_vote_converges` — all vote traffic dropped for the first virtual 500 ms
  then healed; a forced split-vote still converges to one leader.
- `minority_partition_cannot_commit_and_heals` — an isolated leader cannot
  commit; the majority elects and commits past it; heal reconciles.
- `crash_during_truncate_recovers` — a crash mid-truncation recovers to a
  consistent state (inv4 never violated across the crash).
- **`raw_m3_data_plane_phantom_commit_is_caught`** — the oracle's negative pin:
  run against the *shipped M3 receiver's* raw AppendPosition reporting
  (`DataPlane::RawM3`), the sim **catches** an inv5 phantom-commit violation —
  i.e. the sim demonstrably would have caught the exact phantom-commit path the
  M4 receiver contract (genuine-quorum reporting) prevents.
- **`raw_m3_wrong_base_term_stamp_is_caught`** — the second RawM3 pin: a
  current-term segment injected at a divergent base is **caught** by inv2. Both
  RawM3 pins are verified fail-RED (the run stays green) if the oracle's guard is
  removed.
- **`idle_cluster_reconciles_divergent_node_via_gossip_floor`** — a divergent
  node healing into a **fully idle** cluster (zero new submissions) still
  reconciles and truncates, driven purely by the leader's bounded gossip floor
  re-shipping the term map. This is the model-layer twin of the real-node
  `heal_truncates_divergent_tail_and_reconverges` failover test — the exact hole
  the old submit-per-iteration workaround masked.

**Seeded fuzz** — `fuzz_default_seeds` runs seeds 0..50 (3 nodes, 20 000 steps,
2 % drop / 0.5 % dup / 0.05 % crash per event); `fuzz_heavy_seeds` (feature
`sim-heavy`) runs seeds 0..1000, mixing 3- and 5-node clusters at 5 % drop /
1 % dup / 0.1 % crash. Every seed runs the invariant oracle after each event.

## Interpretation

**Verdict: PASS.** Every one of the 10 failovers served in **162.9–394.1 ms**
(p50 **202.1 ms**, p90 279.3 ms, max 394.1 ms — all comfortably < 1 s), and **no
committed byte was lost in any iteration** (`committed loss: none`). This is a
genuine PASS on the metric the gate defines, not a "smoke run" that defers its
verdict — the loopback-representativeness argument above is why.

**The failover interval is timeout-dominated, exactly as designed.** Each number
is essentially `randomized_timeout (150–300 ms) + one vote round-trip + the
NewTerm quorum-commit fsync`. The distribution's center (~200 ms) sits mid-range
of the 150–300 ms timeout window; the 394 ms max (iter 9) is a timeout that
landed high plus one election round that consumed a term without electing
(visible in the term ledger).

**kill→serve and kill→commit-advance are identical every iteration — this is a
correctness statement, not a measurement artifact.** A survivor's `can_serve`
only turns true once its NewTerm frame is quorum-committed (§5.4.2 serving gate),
and that same commit is the first commit-advance past the recorded floor. The two
metrics coinciding is direct evidence that **no node serves before it has
quorum-committed in its new term** — the anti-split-brain / anti-phantom-serve
property. (The `await_serving_among` helper also asserts, throughout, that at most
one survivor ever serves — no split-brain window.)

**Terms consumed = 13 over 10 failovers.** Most failovers bump the term by one;
iters 6 and 7 bumped by two (t8→t10, t10→t12), the signature of one candidate
timing out and bumping the term without winning before a second candidate
succeeds — normal Raft election churn under a randomized timeout, fully safe
(inv1 holds: no term ever had two leaders).

**Truncations observed = 2, not 10 — and that is correct.** A restarted
ex-leader only has a divergent tail to cut if it made inflight (uncommitted)
bytes **durable** before the kill. `crash()` stops the node without a final
flush, so whether the divergent tail reached disk depends on where the archive
agent's `fdatasync` was at the instant of the kill. On the 2 iterations where a
durable divergent tail existed, the restarted node truncated it to the common
prefix before rejoining the data plane; on the other 8 the killed node's durable
frontier was already at or below the committed floor, so there was nothing to
cut. Either way the restarted node rejoined in the current term with a
prefix-consistent log (asserted by the term-adoption wait).

## Corroboration — the real-node partition/failover harness

`uc2_node/tests/failover.rs` (5 tests, green in this run) drives the same real
`Node` API through the M4 claims with **byte-equal journal replay** as the
correctness oracle:

- `boot_elects_exactly_one_leader_and_commits` — single-leader boot, serving gate
  requires quorum commit of the NewTerm frame, 1000 msgs commit on all 3,
  journals replay byte-identically.
- `leader_kill_fails_over_subsecond_without_losing_committed_data` — the direct
  twin of this gate; it printed, in the verification run:
  `FAILOVER kill->serve = 265.259 ms (new leader = node 2, term 2)` — squarely
  inside the gate's 163–394 ms band.
- `minority_partitioned_leader_cannot_commit_phantom` — an isolated leader's
  commit stays pinned while the majority commits past it (real-node inv5).
- `heal_truncates_divergent_tail_and_reconverges` — the idle-reconciliation proof:
  a deposed leader adopts the higher term and truncates its divergent tail driven
  purely by the gossip floor, with **zero** new submissions, and ends
  replay-identical (both NewTerm frames, none of the phantom appends).
- `restarted_follower_recovers_state_and_rejoins` — a restarted node rejoins in
  the current term with no spurious election.

Together the sim (model-layer, 1050+ seeds) and the harness (real-node, byte-equal
replay) bracket the gate's correctness claims; this example supplies the measured
failover *distribution* on top.

## M4-scope notes (carried openly to M5/M6)

- **Buffer prefill is cut to M6.** A node that has fallen below the leader's ring
  tail (a minority-slow follower, not the quorum path) is caught up by the
  NAK/replay path; full snapshot-style prefill is M6.
- **`NoCommonPrefix` → `Fatal` until M6.** If reconciliation finds no common
  prefix at all (a divergence below the durable base), the node fail-stops rather
  than installing a snapshot. That snapshot-install recovery is M6; in M4's
  static-membership, timeout-bounded world it is unreachable (the reconciliation
  analysis in the plan shows the common prefix is always at or above the
  committed floor).
- **Commit is not persisted (M5 restart contract).** The commit counter is
  in-memory; a node that restarts re-derives its safe frontier from durable state
  and the leader's gossip, never from a persisted commit. The M5 follow-ups are
  **truncation-epoch hardening** (fencing a truncate against a stale in-flight
  append across a term change) and the **commit-persistence decision** (whether to
  make commit durable to shorten cold-start re-derivation) — both explicitly
  deferred, neither required for the M4 gate.

## Fleet (3 × c6id, real LAN) — detection-timing confirmation

_**Not yet run.** One node per 16-vCPU c6id host over a real NIC (followers bound
to their concrete private IPs), journals on local NVMe. Because the failover
interval is timeout-dominated (above), the fleet run is expected to reproduce the
~200 ms-class p50 within the wire-RTT delta (a few hundred µs). What the fleet run
**confirms** that loopback cannot: the **real-LAN detection timing** — that a
leader's silence is detected within the 150–300 ms follower-liveness window over
a real NIC (packet-loss-induced late detection, NIC queueing) rather than the
kernel loopback memcpy — and that the NewTerm-commit tail rides real-NVMe fsync
(tens of µs, *lower* than the sandbox's ms-scale ext4, so the fleet p50 should if
anything come in at or below the loopback number). It will be appended here when
performed._
